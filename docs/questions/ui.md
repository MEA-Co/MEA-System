# 질문·질문지·응답 입력과 UI

질문지는 `questionnaires`, 원본 질문은 `questions`가 본체이며 별도 버전을 만들지 않는다. 데이터 계약은 [저장 구조](data-api.md), 최신 운영 적용 상태와 배포·검증 절차는 [운영 안내](operations.md)를 따른다. 아래 이전 날짜의 운영 적용 대기 기록은 당시 상태다.

## 서술형 탐구활동 참조 권장

각 서술형 답변 열의 설정에 `탐구활동 참조 권장` 체크박스를 둔다. 기본은 해제이며 체크/해제를 저장·재조회할 수 있다. 옵션을 켜면 질문 및 질문지 미리보기의 해당 답변 입력에 포커스하면 파란 테두리와 파란 말풍선을 표시한다. 말풍선은 `탐구활동 참조가 필요한 질문입니다.`와 `@탐구활동 을 입력하여 탐구활동을 언급하며 답변해주세요!` 두 줄이며 포커스를 벗어나면 숨긴다. 다른 답변 유형으로 바꾸면 옵션을 제거한다. 권장 안내이며 탐구활동 첨부를 필수로 요구하지 않는다.

설정은 기존 `questions.fields` JSONB의 `explorationRecommended` boolean으로 저장한다. API 스키마와 DB 검증 함수가 서술형에만 허용한다. 기존 필드에 속성이 없으면 해제로 해석하며 데이터 일괄 변경은 하지 않는다. 로컬 migration `20261001034040_question_text_exploration_recommendation.sql`, 운영 순서는 `operations.md`의 같은 날짜 절을 따른다.

## 진입점과 파일 구조

대시보드 페이지 키는 `questions` 하나다. 이전 `view=questionnaire` 접근 항목·별도 렌더러·아이콘·호환 분기는 제거했다. 이전 URL은 다른 미지원 view와 같이 역할별 기본 화면으로 처리한다. `questionnaires` 탭 값과 `/api/questionnaires`는 현행 질문지 기능이므로 유지한다.

| URL (`/dashboard` 기준)                                         | 화면                                                      |
| --------------------------------------------------------------- | --------------------------------------------------------- |
| `?view=questions`                                               | 리드·관리자: 통합 질문지 목록. 컨설턴트: 기존 배포본 목록 |
| `?view=questions&tab=questions`                                 | 질문 목록                                                 |
| `?view=questions&question=<ID 또는 new>`                        | 질문 생성·수정 Drawer                                     |
| `?view=questions&tab=questionnaires`                            | 통합 질문지 목록                                          |
| `?view=questions&tab=questionnaires&draft=<질문지 ID 또는 new>` | 질문지 편집·조회                                          |
| 위 상세 URL에 `&questionnairePanel=responses`                   | 배포본의 제출된 답변 탭으로 이동                          |

리드·관리자의 기본 진입 화면은 통합 질문지 목록이며 공통 데이터 관리 분류와 화면 제목·설명 아래에서 질문/질문지 영역을 전환한다. 질문지 개수와 정렬 안내는 검색창 위에 표시한다. 기존 관리 진입 카드와 별도 검토 중·배포 목록은 통합했다. 전체는 수정 중(본인) 최대 2개, 검토 중(본인·공유) 최대 2개, 배포 최대 10개 순서로 묶으며 단계 제목에는 조건에 맞는 전체 개수를 표시한다. 각 단계의 전체 보기는 해당 상태 목록으로 이동한다. 전체는 페이지네이션 없이 최대 14개, 개별 상태는 10개씩 표시한다. 수정 중·검토 중은 최근 수정순, 배포는 최근 배포순이다. 보관은 본인 문서만 별도 상태 탭에서 표시한다.

단계 제목 옆의 보조 설명은 표시하지 않는다. 단계 머리글은 전체 보기 버튼 유무와 무관하게 내부 최소 높이 2rem과 동일한 세로 여백을 유지한다. 단계 머리글과 상태 Select는 수정 중 옅은 노랑·검토 중 옅은 초록과 진한 초록 글자·배포 옅은 파랑과 진한 파란 글자로 통일한다.

상태는 공통 shadcn Tabs의 전체/수정 중/검토 중/배포/보관 단일 선택이다. 제목 검색과 전체 작성자/내가 작성한 질문지 필터를 제공하며 상태 이동 시 조건을 유지하고 페이지는 1로 돌아간다. URL의 `qStage`, `qSearch`, `qOwner=mine`, `qPage`로 조건을 유지한다. 상세 열기·닫기와 새 질문지 작성에도 조건을 보존한다. 타인 미확인 검토 중·배포본과 새 검토 요청의 파란 알림을 유지하며 실제 상세 화면에서만 읽음 처리한다. 목록 조회는 읽음 처리하지 않는다.

파일은 `app/(private)/dashboard/_views/questions/` 아래에 둔다.

| 책임                            | 위치                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------- |
| 통합 진입점                     | `QuestionsView.tsx`                                                                     |
| 독립 질문 제작·목록·미리보기    | `components/question/`, `hooks/`, `lib/`                                                |
| 질문지 제작·검토 중·기존 응답·알림 | `components/questionnaire/`                                                             |
| 질문지 목록 계산                | `lib/questionnaire/list-server.ts` (서버 목록·ID 조회), `list-model.ts` (URL 정규화)                 |
| 질문지 저장·갱신                | `hooks/questionnaire/`, `lib/questionnaire/`                                            |
| HTTP 연결                       | `app/api/questions/[[...path]]/route.ts`, `app/api/questionnaires/[[...path]]/route.ts` |

이전 `_views/questionnaire/` 전체와 미사용 `PublishQuestionnaireButton`은 제거했다. 이름에 questionnaire가 있어도 위 현행 구조의 파일·API·DB는 삭제 대상이 아니다.

## 관리 목록 UI

독립 질문 목록·통합 질문지 목록은 학습법/탐구활동과 같은 `CollectionHeader`, `CollectionSearch`, `CollectionPagination`을 사용한다. 생성 버튼은 목록 제목 옆에 배치하고 모바일에서는 “추가”로 축약한다. 원본 질문의 Drawer를 닫을 때에는 기존 열기 버튼 또는 목록 제목으로 포커스를 돌린다.

- 표는 공통 shadcn `Table`의 회색 머리글·흰색 행·외곽 테두리를 사용한다. `CollectionTableState`는 표 머리글을 유지한 채 로딩 스켈레톤·빈 결과·오류/재시도를 표시한다. 최소 본문 높이는 18rem이며 실제 행 수·내용에 따라 표는 더 높아질 수 있다.
- 모바일 질문 표는 제목 아래에 참조/사용 배지·관리자 화면의 제작자를 모으고 삭제는 별도 관리 열에 둔다. 데스크톱 질문지 표는 질문지/상태 변경/바로가기·삭제 세 열을 사용한다. 모바일은 제목·작성자·날짜를 전체 너비에 두고 아래 줄 왼쪽에 상태 Select, 오른쪽에 바로가기·삭제를 모은다. 바로가기는 작성(연필)·열기(눈)·제출 응답 보기(응답) 아이콘 버튼으로 통일하고 제출 수는 숫자 배지로 표시한다. 버튼에는 동작을 설명하는 접근성 이름과 title을 제공한다. 모바일 열 머리글은 숨기며 단계 머리글·빈 결과의 colspan=3 구조는 유지한다.
- 질문의 테이블/그래프 전환과 일반 컨설턴트의 제출 전/제출 완료 전환은 공통 shadcn `Tabs`를 사용한다. 그래프 내용과 관계 계산은 기존 그대로다.
- 참조/사용 표시는 무채색, 미처리 검토 수는 옅은 노랑 `Badge`로 표시한다. NEW·새 검토 요청과 미확인 행의 파란 알림 의미는 유지한다. 화면 표시만 바뀌며 읽음 기록·요청 처리 조건은 바꾸지 않는다.
- 질문 목록은 기존 서버 검색/10개 페이지를 유지한다. 통합 질문지 목록도 서버에서 제목 검색·작성자 필터·정렬·개수·페이지를 처리한다. 전체 단계 요약은 수정 중/검토 중/배포 각 2/2/10개이고 상태별 목록은 10개 페이지다. 컨설턴트 제출 전/완료 탭도 10개씩 조회한다. 전체 개수는 현재 페이지 길이가 아니라 서버 집계를 사용한다. 상세는 목록과 별도 조회한다.

### 컨설턴트 질문지 목록

컨설턴트 목록도 공통 `CollectionTable`과 `CollectionTableState`를 사용한다. 데스크톱은 질문지 제목·배포일, 답변 상태, 열기 열로 구성하고 모바일은 상태를 제목 아래에 모으며 열기 버튼을 아이콘으로 표시한다. 행 클릭과 제목·열기 링크는 같은 상세로 이동한다. 제목은 긴 경우 줄바꿈하고, 미작성/작성 중/제출 완료를 구분한다. 새 질문지의 파란 NEW 배지는 유지하며 전체 신규 개수는 탭 아래 목록 개수 옆에 표시한다.

제출 전/완료 Tabs, 서버 10개 페이지, URL 조건과 읽음 처리 계약은 유지한다. 로딩·빈 목록도 표 머리글과 동일한 본문 최소 높이를 사용하고 페이지 이동 영역은 표에서 여백을 두어 분리한다. 실제 브라우저 검증은 별도 요청 시 진행한다.

## 질문 제작과 목록

질문 제작의 답변 표시 방식·행 수 설정 및 조건 내부 표면은 공통 `Card`/`CardContent`를 사용한다. 노란 상단 선은 `accent` variant로 관리하며 기존 여백·입력 배치를 유지한다. 참조 권장·선택형/척도형 설정·설명 공개/제목 라벨은 공통 `Label`로 통일한다. 질문 본문과 설명 표면은 미리보기와 공유하는 스타일을 계속 사용한다.

저장된 가이드 응답이 있는 열의 삭제/유형 변경 및 저장 시 새 가이드 응답 발견은 공통 `AlertDialog`로 확인한다. 취소를 초기 포커스로 두고 배경 입력·스크롤을 차단하며 닫힘 중에도 안내 문구를 보존한다. 열 변경 취소는 원본을 유지하고 저장 중 확인 취소는 자동 저장을 중지한다. 승인 시 기존 saveId/revision과 확인된 필드 ID로 재시도하며 서버의 답변 보호 계약은 유지한다. 확인 중 뒤로가기는 현재 편집기를 유지하여 작성 취소 확인창과 겹치지 않는다. 브라우저 이탈/새로고침 보호는 기존 네이티브 확인 경로를 유지한다.

질문 제작·편집(독립 Drawer 및 질문지 내부 제작)은 실제 질문지 미리보기와 공통 회색 캔버스 및 모바일/PC 바깥 여백을 사용한다. 기본 정보는 흰 Card, 질문 구성은 미리보기와 같은 흰 배경·노란 상단 선 카드로 표시한다. 입력 필드의 회색 배경과 기존 내용·설정·저장 동작은 유지한다. 관리용 이름·답변 설정 카드도 노란 상단 선을 사용한다. 제작 화면의 기본 정보 헤더 및 질문과 답변 구성 제목/설명은 생략하고, 질문 입력 왼쪽 번호 자리는 #으로 표시한다. 실제 질문지의 질문 번호는 그대로 유지한다. 조건 설정은 질문·답변 구성 카드 밖의 별도 accent 카드로 분리한다.

리드는 본인이 만든 질문만 본다. 실제 관리자는 관리자 화면에서 전체 질문과 제작자 이름을 본다. 관리자도 리드 화면으로 전환하면 서버 조회를 본인 질문으로 좁히며 제작자 열은 숨긴다. 표시 역할은 실제 DB 권한을 부여하거나 변경하지 않는다. 일반 컨설턴트와 학생에게 독립 질문 목록은 제공하지 않는다.

질문 목록은 최근 수정 순, 서버 페이지당 10개다. 관리용 이름과 질문 본문의 일반 텍스트를 검색하며 입력 후 300ms 디바운스를 적용한다. 공백을 정리한 검색어 전체의 부분 일치이며 대소문자를 구분하지 않는다. 한글 부분 검색은 가능하지만 초성·오타·형태소 검색은 아니다. `%`, `_`, 역슬래시는 문자로 검색한다. 설명·답변 열·선택지는 검색 대상이 아니다. 검색 변경 시 첫 페이지로 이동한다.

테이블은 질문, 참조 중인 질문, 사용 중인 질문지, 관리 열을 표시한다. 참조·사용 수는 각각 배지 하나와 목록 툴팁으로 표시한다. 사용·참조 중이면 삭제 버튼을 비활성화하고 툴팁으로 이유를 안내한다. 독립 질문 삭제 API는 현재 `archive_question`을 사용해 목록에서 제외하는 보관 방식이다. UI의 삭제 표현이 물리 삭제를 뜻하지는 않는다. 그래프는 관계 전체가 필요해 별도 전체 조회·클라이언트 검색을 사용한다.

질문 생성·수정은 Drawer에서 진행하고 목록 검색·페이지 상태를 유지한다. 저장 상태/자동 저장 안내와 닫기·저장 버튼은 학습법·탐구활동처럼 흰색 하단 고정 영역에 배치한다. 질문지 내부 제작의 배치 버튼도 같은 하단 영역에 표시한다. 미저장 종료 확인은 독립/질문지 내부 제작 모두 Drawer 내부 공통 AlertDialog를 사용하며 계속 작성에 초기 포커스를 둔다. 안내 문구는 고정하여 초안 삭제와 닫힘 애니메이션 중 변경되지 않는다. 확인 중 편집 영역은 inert와 스크롤 잠금을 적용한다. 본문은 필수, 관리용 이름은 선택이며 비어 있으면 본문 텍스트를 표시 이름으로 사용한다. 새 문서를 전혀 바꾸지 않았으면 저장 버튼은 비활성이고 바로 닫힌다. 다른 내용을 수정하면 저장 시도와 닫기 확인을 제공하지만 본문이 비어 있으면 저장 불가 이유를 안내한다. 수동·자동 저장 실패는 토스트로 표시한다. 미완성 입력은 서버에 저장하지 않으며 로컬 임시 복구와 저장 중 입력 보존을 유지한다.

답변 열은 서술형·척도형·단일선택형·다수선택형 네 가지만 지원한다. 탐구활동·학습법은 서술형 본문의 `@언급`으로 연결한다. 열·선택지 ID는 표시 순서와 별개다. 선택형은 목록/칩과 직접 입력 항목을 지원하고 직접 입력은 일반 선택지 다음에 표시한다. 신규 독립 질문에서 추가 서술은 별도 서술형 열로 구성한다. 독립 첨부형 `exploration`·`study`는 기존 저장 데이터에서도 서술형으로 전환했으며 API·DB에서 새로 저장할 수 없다. 미리보기 입력은 저장하지 않는다.

단일·반복 행과 최소/최대 행 수, 순서별 행 이름을 설정한다. 이름 설정은 테이블 UI이며 미지정 이름은 숫자다. 행 이름은 답변 식별자가 아니다. 참조형 행 수는 앞선 질문의 응답을 따른다.

답변 표시 방식 Select는 기본 그룹의 `카드`·`표`와 프리셋 그룹의 `흐름표`를 구분한다. 표시 명칭과 목록 그룹만 변경하며 저장값 `cards`·`table`·`flow` 및 동작은 유지한다. 표 선택형 설정에서 드롭다운 사용 안내 문구는 생략하고 선택지·직접 입력 설정은 그대로 제공한다.

조건은 공통 Select로 질문 → 특정 열/모든 열 → 조건 순서다. `응답했을 때`는 특정 열 또는 같은 행의 모든 열을 검사한다. `선택했을 때`는 직접 입력 없는 선택형 열에서만 제공하고 단일은 equals, 다수는 includes로 저장한다. 앞선 응답 참조를 켜면 일치하는 원본 행만 ID 기준으로 반복한다. 조건 변경으로 숨겨진 미리보기 답변은 다른 행의 값을 덮어쓰지 않는다.

`조건 해제` 버튼과 조건 메뉴의 `조건 없음`은 조건·응답 참조·선행 연결을 함께 해제한다. 선택 대상이 목록에 없어도 해제 버튼을 사용할 수 있다. 참조형은 단일 행 설정으로 돌아가며 일반 표·흐름표의 직접 설정한 행/시기는 유지한다. 해제한 후속 질문을 저장해야 원본의 열 구성 수정 제한이 풀린다. 다른 참조가 남아 있거나 배포 잠금이 있으면 계속 제한하며, 참조 체인은 마지막 후속 질문부터 해제한다. 이 정책상 저장 거절은 실제 revision 충돌과 구분해 같은 편집기에서 재저장할 수 있다.

설명은 질문 본문·답변과 분리된 `question_details`에 저장한다. 제목·서식 본문·공개 여부를 설정하며 미리보기에는 공개 설명만 표시한다. `save_question`이 질문과 설명을 원자적으로 저장한다. details 생략은 보존, 빈 배열은 삭제다.

## 질문지 제작

### 질문지 안내

기존 ‘시작 안내’를 ‘안내’로 통일한다. 질문지 처음·각 질문 다음·질문지 마지막의 `안내 추가`로 여러 개(최대 50개)를 넣는다. 각 안내는 제목·서식 본문·위치 선택·삭제와 학습법/탐구활동/탐구줄기 등록 버튼 표시 및 문구 설정을 제공한다. 위치는 질문 배치 ID에 연결하므로 질문 이동을 따라가며, 기준 질문이 삭제되면 안내를 마지막에 표시하여 내용을 보존한다. 같은 위치의 안내는 등록 순서대로 표시한다. 기존 시작 안내는 첫 위치의 안내로 유지한다.

안내는 질문 번호·질문 개수·답변·최종 제출본·PDF에 포함하지 않는다. 등록을 강제하거나 완료 개수를 검사하지 않는다. 학습법과 탐구활동은 기존 등록 Drawer를 사용한다. 탐구줄기 버튼은 작성 화면에서는 질문지 구성을, 응답 화면에서는 작성 중인 답변을 저장하고 `/dashboard?view=exploration&tab=links&linkEditor=new`로 이동한다. 검토 중 제작자의 응답 미리보기에서는 답변과 질문지 구성 모두 저장한다. 읽기 전용 조회에서는 저장할 입력 없이 이동한다. 저장 중 중복 이동을 차단하며 실패·충돌·미확인 저장·저장 도중 추가 변경이 남으면 이동하지 않고 토스트로 안내한다. 답변은 제출하지 않고 작업 내용만 저장한다.

일반 질문지와 같은 작성 권한·revision·충돌 보호를 사용하며 배포/보관 상태의 구성은 편집할 수 없다. 새 `study_registration` 질문 저장 금지와 기존 답변 ID는 유지한다.


## 검토와 검토 요청

현재 상태 Select는 작성자의 수정 중↔검토를 허용하고, 검토 중인 본인 질문지는 확인 후 실제 배포한다. 확인 창에서 질문지 구성과 포함된 원본 질문·설명·답변 설정이 수정/삭제 불가가 됨을 안내한다. 같은 원본을 사용하는 다른 질문지에서도 질문 수정은 막힌다. DB가 원본 질문별 미처리 검토 요청을 재검사하며, 읽음 여부·출처 질문지와 무관하게 미처리가 있으면 배포 전체를 롤백한다. 배포 시 원본에 publication_locked_at을 설정하고 원본·설명 변경을 DB 트리거로 차단한다. 배포본 구성은 기존 불변성 트리거로 보호한다. 작성자와 관리자는 보관 메뉴로 질문지를 숨길 수 있다. 보관 시 컨설턴트의 목록·상세 조회와 응답 저장이 차단되며, 질문지 내용·기존 응답·배포 원본 잠금은 유지한다. 작성자는 내 질문지 목록의 보관 필터에서 보관 전 상태로 복원할 수 있다. 배포본을 복원하면 컨설턴트에게 다시 표시된다. 배포본은 저장된 응답이 없으면 작성자가 같은 ID로 검토 중 또는 수정 중으로 되돌릴 수 있다. 임시저장도 응답으로 보호하며, 단순 열람의 빈 세션은 되돌리기를 막지 않는다. 검토 중 가이드 응답은 이 판정에서 제외하고 보존한다. 되돌리면 컨설턴트 목록에서 사라지며 다른 배포본에서 쓰지 않는 원본만 잠금을 해제한다. 기존 배포본에서 수정용 복사본을 만들던 동작은 이 복귀 동작으로 대체한다.

컨설턴트는 배포 목록과 상세에서 질문과 공개 설명을 열람한다. 비공개 설명과 독립 원본 질문 조회 권한은 제공하지 않는다. 새 배치형 배포본은 답변 입력과 저장·제출을 제공한다. 저장(자동 저장 포함)은 본인 전용이며 제출하면 리드·관리자에게 공개된다. 제출 후에도 수정할 수 있고 저장만 하면 마지막 제출 내용이 유지되며 재제출할 때 공개 내용이 갱신된다. 리드·관리자는 통합 질문지 목록의 배포 단계에서 제출된 답변을 조회한다. 단순 열람은 빈 세션만 만들며 저장 이력으로 취급하지 않는다. 이 기능의 migration `20261002074415_distributed_response_submissions.sql`은 로컬 적용 완료, 운영 적용 대기다. 기존 구형 배포본 응답 기능은 유지한다. 질문 제작의 내용 불러오기는 원본과 별개의 새 질문을 만든다.

검토를 시작하면 질문지와 포함된 원본 질문을 다른 리드·관리자에게 공개한다. 다른 리드도 같은 질문지 편집기에서 구성·안내·원본 질문·설명을 수정할 수 있다. 원본 변경은 그 질문을 재사용하는 다른 질문지에도 반영된다. 단, 다른 배포본에 포함되어 잠긴 원본은 누구도 수정할 수 없다. 상태 변경은 작성자만 가능하고 삭제·보관은 기존 작성자/관리자 정책을 따른다. 검토본의 돌아가기는 조건을 보존한 통합 질문지 목록으로 연결한다.

원본 설명은 질문 편집기와 save_question에서 원자적으로 관리한다. 검토 요청은 원본 질문에 귀속되며 질문지 출처와 무관하다. 원본 작성자 외의 리드·관리자가 요청하고 원본 작성자·관리자가 처리한다.

## 가이드 응답

지정 가이드 계정은 검토본에서 실제 응답을 저장하고 다른 리드는 저장 없는 미리보기를 사용한다. 가이드 답변은 질문 미리보기의 설명 아래 접힘 영역에 표시하며 서식과 행 이름을 유지한다.

최신 검토본의 제목·섹션·질문·순서를 조회하고, 5초 간격 및 포커스 복귀 시 갱신한다. 남아 있는 동일 ID·유형의 미저장 입력은 보존한다. 완료 상태에서도 가이드 답변은 수정할 수 있다.

질문 본문 수정·답변 항목 추가는 기존 답변을 유지한다. 가이드 답변이 있는 항목을 삭제하거나 유형을 바꾸면 먼저 확인하고 해당 답변만 삭제한다. 질문·섹션 제거도 가이드 답변이 있으면 확인하며 해당 질문지의 응답만 삭제한다. 다른 질문지의 응답은 유지한다. 제거 후 다시 배치한 질문은 빈 응답으로 시작한다. 이전 답변 보관·복구나 구조 변경 재작성 안내는 제공하지 않는다.

## 리치 텍스트 탐구활동 명령어 (2026-10-01)

모든 공통 리치 텍스트 입력에서 `@` 또는 `@탐구활동`을 입력하면 명령어 메뉴가 표시된다. `탐구활동 참조 권장`과 무관하며 권장 옵션은 기존 파란 안내만 제어한다. 클릭 또는 방향키/Enter로 선택하고 Escape로 닫는다. 선택하면 입력창 위에 본인 탐구활동 목록·검색과 `탐구활동 추가` 버튼을 표시한다. 추가는 기존 작성 Drawer를 열며 임시저장/확정 기능을 재사용한다. 확정 활동만 답변에 첨부할 수 있고 임시저장 활동은 작성 후 확정해야 한다.

명령어 메뉴도 공통 Base UI Popover의 Portal과 fixed 위치를 사용하여 일반 표·흐름표의 스크롤 영역에 잘리지 않는다. 입력창을 기준으로 화면 여유에 따라 위/아래 위치를 조정하고 사용 가능한 높이 안에서 스크롤한다. 열 때 입력 포커스를 옮기지 않으며 입력창과 메뉴 사이 키보드 이동을 허용한다. Escape는 입력창으로 돌아가고 바깥 클릭은 클릭한 곳의 포커스를 유지한다.

첨부한 활동은 RichText의 `explorationReference` mark에 UUID를, text에 활동명을 저장한다. 기존 text 노드와 저장/자동 저장 경로를 사용하므로 DB migration은 없다. 본문 추출 시 활동명이 유지되며 열람 화면에서는 활동명을 눌러 기존 조회 권한 범위 안에서 상세를 연다. 삭제되거나 권한이 없는 활동은 안내를 표시하고 저장된 활동명은 유지한다. 원본 활동 수정은 저장된 표시 이름을 자동 변경하지 않는다. 새 배치형 배포는 활성화하지 않는다.

검증: 타입 검사, 변경 파일 린트, RichText/질문지 저장 회귀 22개, 예시 데이터를 사용한 브라우저 명령어·첨부·새 작성 Drawer 확인. 실제 로그인 계정의 저장/재조회 실사용 검증은 아직 하지 않았다.

첨부 목록 UI 보완: 입력 위에 겹쳐 뜨는 Portal 팝업을 사용하며 주변 레이아웃을 밀지 않는다. 카드에는 주제·학년·학기·기재 영역만 표시하고 카드 전체 클릭으로 첨부한다. hover/키보드 focus 시 `첨부하기` 문구를 보여준다. `탐구활동 추가`는 목록 마지막 항목이며 목록 제목은 제거했다. 명령어에 아이콘·짧은 설명을 추가하고 팝업과 참조 권장 말풍선에 X 닫기를 제공한다. 사용자 요청에 따라 이번 수정에는 브라우저 테스트를 실행하지 않았다.

첨부 참조 삭제: Backspace/Delete 및 모바일의 같은 삭제 입력은 `@활동명` 전체를 한 번에 지운다. 일부 글자만 선택한 경우에도 참조 전체로 삭제 범위를 확장하며, 참조 바깥의 일반 텍스트는 기존 삭제 동작을 유지한다. 기존 mark 저장 형식은 유지한다.

탐구활동 조회: `useExplorationList`의 객체 응답과 `exploration-list-v1`+요청 URL 캐시를 사용한다. 첨부 입력/선택기는 서버 검색·10개 페이지를 사용하고, 선택된 ID는 별도 단건 조회로 유지한다. @ 메뉴의 작성 진입은 context만 읽으며 열람 참조는 reference 경로로 0~1건을 읽는다. 신규 조회 함수 `20261013094552_exploration_query_contract.sql`을 앱 배포 전에 적용해야 한다. 권한·요청 계약·검증·최신 적용 순서는 [탐구활동 문서](../exploration/data-api.md#서버-검색페이지-api-2026-10-13)를 따른다.

## 진로 흐름 스레드 입력 (2026-10-04)

`responseRequirements.kind=career_flow`인 질문(기존 진로 흐름 원본과 내용 불러오기로 만든 복제)은 공통 QuestionBlockPreview에 ‘스레드로 응답하기’와 ‘표로 응답하기’를 나란히 표시하고 각각 별도 팝업을 연다. 두 화면은 동일한 행·열 답변 상태를 공유한다. 읽기 전용에서는 각 버튼이 ‘스레드로 답변 보기’·‘표로 답변 보기’로 표시되며, 팝업을 닫아도 입력과 선택 시기를 유지한다. 고교 입학 전 필수 카드에서 중등 또는 예비 고1을 선택하며, 고3 수시 원서 접수 시기는 항상 표시한다. 학기를 펼쳐 선택 시기를 추가한다. 기존 답변이 있는 시기는 자동 표시하고, 시작 시기를 전환해도 입력을 지우지 않는다. 입력이 없는 선택 카드만 숨길 수 있다. 빈 선택 카드의 표시 상태는 화면 상태이며 다시 열 때 저장되지 않는다.

제출 UI와 DB는 중등/예비 고1 중 한 시기와 수시 원서 접수 시기에 각각 한 항목 이상 작성했는지 검사한다. 임시 저장은 부분 입력을 허용한다. 필수 시기 ID는 질문의 responseRequirements에 저장하며 복제 시 새 열 ID로 매핑한다. 필수 시기 열을 삭제하거나 서술형이 아닌 유형으로 바꾸는 저장은 거절한다. 전용 입력 디자인과 팝업은 유지하며 원본 UUID는 원본 전용 예시 placeholder 선택에만 사용한다.

시기별 카드가 기존 행 ID와 열 ID를 그대로 사용한다. 선택하지 않은 시기의 ‘변화 없음’은 화면상 해석이며 답변을 자동 생성하거나 복사하지 않는다. 기본 세 항목과 접힌 추가 항목(대입 영향·조언)을 제공하고 기존 추가 항목 응답은 펼쳐 표시한다. 서식·탐구활동 참조는 기존 입력기를 사용한다. 표 팝업은 중등·예비 고1과 수시 원서 접수 시기를 기본 표시하고, 빈 선택 학기는 추가하기 버튼과 빗금 배경으로 표시한다. 추가하기에서 세부 시기를 선택하면 해당 열만 추가되며, 남은 시기는 같은 학기의 추가하기로 선택한다. 기존 답변이 있는 열은 자동으로 표시한다. 중등·예비 고1은 ‘고교 입학 전 / 두 시기 중 하나 입력 필수’ 병합 머리글로 묶고, 마지막 두 답변 항목은 옅은 색과 ‘(선택)’으로 표시한다. 작성 예시 켜기/끄기와 모든 시기 펼치기/빈 시기 접기를 지원하며 예시는 저장하지 않는다. 정의에 없는 시기(예: 대학 전과)를 임의 추가하지 않는다.

필수 조건의 현재 DB 계약은 아래 응답 무결성·조회 구조 절과 저장 구조 문서를 따른다. 실제 브라우저 검증은 진행하지 않았다.

### 질문 검토 요청 (2026-10-02)

검토 요청은 질문지 배치가 아닌 원본 질문에 귀속한다. 같은 질문의 요청은 여러 질문지·질문 편집 화면에서 공유한다. 검토 중인 질문에는 리드/관리자가 요청을 작성하고 원본 질문 작성자 또는 관리자가 처리 완료한다. 가이드 답변 작성 권한과 별개다. 완료 내역은 접어 표시하고 질문 수정으로 자동 처리하지 않는다. 질문 목록에 미처리 개수를 표시한다. 운영 적용과 DB 계약은 operations.md의 최신 절을 따른다.

검토 요청의 미확인 여부는 question_review_reads로 제작자별 관리한다. 목록·대시보드에 파란 새 요청 표시가 나오며 요청 카드가 실제 화면에 표시되면 해제한다. 처리 완료와 읽음은 구분한다.

공통 `QuestionReviews`의 바깥 카드는 기본 배경에 질문 카드와 같은 두께의 초록색 상단 테두리를 사용한다. 실제 미처리 요청 내용이 담긴 내부 박스에만 옅은 초록색 배경을 적용하고 완료 이력은 기본 배경을 유지한다. 질문 편집기와 질문지 화면에 동일하게 적용하며 어두운 테마도 대응한다.

최신 정책(2026-10-02): 검토 요청 본인 작성 차단과 새 알림 수신자는 질문지 제작자가 아닌 원본 질문 제작자다. 일반 리드는 본인 질문만 조회·배치하므로 통상 동일하지만 관리자는 타인의 질문도 배치할 수 있다. 검토 중인 질문지의 타인 질문 공유 조회는 독립 질문 관리 접근 권한과 구분한다.

통합 질문지 목록의 배포 단계는 전체에서 최대 10개, 배포 상태 목록에서는 10개 페이지로 표시한다. 제목 검색·배포일·제출된 응답 수를 제공하며 제출 수 버튼은 배치형 배포본의 제출된 답변 탭으로 바로 연결한다. 제출 수는 임시 저장을 제외한 응답자별 마지막 제출본 개수이며 재제출은 중복 집계하지 않는다. 집계 RPC는 리드·관리자만 실행한다. Migration: `20261002081911_distributed_submission_counts.sql` (로컬 적용, 운영 사용자 적용 대기).

현행 로컬 정책(2026-10-15): 원본 질문 작성자는 요청할 수 없으며, 그 외 리드·관리자는 활성 검토 중 질문에 요청할 수 있다. 질문지 작성자 여부는 판정하지 않는다. 처리 권한은 원본 작성자·관리자다. 이전 출처 작성자 차단 정책은 `20261015055947_question_owned_reviews.sql`로 대체한다. 운영 적용은 운영 문서를 따른다.

- 과거 진로 흐름의 한 칸 제출 예외(`20261002083415_career_flow_partial_submission.sql`)는 2026-10-15 응답 무결성 migration으로 대체했다. 기존 제출본을 취소하거나 다시 쓰지 않으며 이후 제출/재제출부터 화면과 같은 두 필수 시기 그룹을 검사한다.

## 표형 응답 제작 (2026-10-11)

일반 표의 선택 열은 옅은 회청색 머리글·셀 배경과 `(선택)` 배지로 구분해 필수 항목보다 강조를 낮춘다. 긴 셀 placeholder는 한 줄 말줄임으로 칸 안에 표시하고 실제 답변은 계속 줄바꿈·높이 확장을 허용한다. 응답 화면에는 최소 작성 수와 최대 행 수 안내를 표시하지 않으며, 반복 답변의 추가 버튼에도 현재/최대 수치를 표시하지 않는다. 제작 설정과 실제 행 추가·삭제·제출 제한은 유지한다.

독립 질문과 질문지의 공통 질문 제작 화면에서 답변 표시 방식을 카드·일반 표·흐름표로 선택한다. 기존 질문의 기본은 카드이며 기존 질문지를 자동으로 바꾸지 않는다. 일반 표는 답변 열 제목을 가로 머리글로 표시하고 셀에서 바로 입력한다. 제작자는 열별 필수 입력, 최소 작성 행 수, 처음 표시할 행 수, 최대 행 수(20 이하)를 지정한다. 최소 작성 행 수가 5이면 응답 화면에도 적어도 5행을 표시한다. 초기 표시 행 수가 최소보다 크면 남는 빈 행은 작성 필수가 아니다. 응답자는 최대 이하에서 행을 추가하고 최소를 유지하는 범위에서 삭제할 수 있다. 답변이 있는 행을 삭제할 때 확인한다.

카드형 반복 답변은 처음 표시되는 첫 번째 행을 기본으로 펼친다. 조건 충족 후 나타나는 참조 행도 첫 행을 펼치며 사용자가 접거나 다른 행을 선택한 뒤에는 입력/재렌더링으로 그 선택을 덮어쓰지 않는다. 행 추가 시 새 행 펼침과 제출된 답변의 전체 읽기 표시는 유지한다. 펼침 상태는 화면 상태이며 저장되는 응답 행·본문을 변경하지 않는다.

일반 표의 행 추가는 카드형과 같은 `+ 항목 추가`로 표시한다. 표 외곽선 안의 하단 전체 너비에 흰 배경·실선 구분 버튼을 두며 가로 스크롤 시에도 버튼 전체가 보인다. 카드형의 항목 추가 위 구분선도 실선으로 통일한다. 추가 가능 조건과 최대 행 제한은 유지한다.

흐름표는 행 이름을 가로의 시기 머리글로, 답변 열을 세로의 답변 항목으로 표시한다. 기본 시기의 이름과 개수는 제작자가 설정하고 응답자는 기본 시기를 삭제하지 않는다. 제작자가 허용한 위치에는 아래 중간 시기 추가 기능을 사용할 수 있다. 모든 기본 시기를 표시하되 최소 작성 시기 수만큼 한 칸 이상 작성하면 제출할 수 있다. 각 시기의 모든 칸을 채우지는 않아도 된다. 앞선 응답의 행을 참조하는 구성에는 일반 표를 사용할 수 있고, 시기를 고정하는 흐름표는 선택하지 않는다.

서술형은 기존 서식·`@탐구활동`·`@학습법` 입력을 사용한다. 일반 표·흐름표의 단일선택형·다수선택형은 셀 안의 드롭다운으로 표시하며 선택 해제와 직접 입력 항목을 지원한다. 다수선택형의 기존 직접 입력 답변 여러 개는 다른 선택지를 추가·해제해도 내용과 ID를 유지한다. 제작자는 답변 유형을 선택형으로 바꾸고 선택지를 설정한다. 카드에서는 기존 목록·칩 설정을 유지한다. 선택형·척도형은 기존 값 형식을 유지하며 드롭다운 표시에는 별도 DB 변경이 없다. 표는 가로 스크롤과 머리글 고정을 제공한다. 열 제목·시기 이름만 고쳐 다른 추천 목록이나 성적 흐름표를 만들 수 있다. 특정 질문 ID에 연결된 기존 진로 흐름 화면은 기본 카드 설정에서 기존 동작을 유지한다.

설정은 `questions.answer_layout`(`cards`/`table`/`flow`), `initial_rows`와 기존 `min_rows`·`max_rows`·`row_labels`에 저장한다. API 문서는 `answerLayout`·`initialRows`를 사용하고 열별 필수 여부는 `fields[].required`(생략 시 필수)로 저장한다. 표시 전환만으로 기존 필드·응답 행 ID를 바꾸지 않는다. 빈 기본 행을 표시하는 초기화는 자동 저장하지 않는다. 표·흐름표는 빈 행을 활성 답변에서 제외하고 최소 작성 행/시기 수를 서버에서 검사한다. 작성된 일반 표 행은 필수 열을 채워야 하며 선택 열과 흐름표의 입력된 값도 유형 검증을 거친다. 제출된 흐름표는 빈 시기의 자리와 원래 ID를 유지하며 조건상 비활성 입력은 빈 자리로 대체해 공개하지 않는다.

Migration: `20261011143258_question_answer_layouts.sql`. 앱 타입·변경 파일 린트·표 설정/행 표시·기존 행 참조·입력 보존·RichText·배포 응답 폼 JS 회귀 29개·Webpack 빌드 통과. 2026-10-12 사용자의 승인에 따라 에이전트가 운영 함수 치환 기준 10개와 외부 웹훅 부재를 확인하고, 임시 migration과 신규 `question_answer_layouts.sql` 회귀를 한 트랜잭션으로 시험·롤백한 뒤 이 migration 한 개를 영구 적용했다. 적용 후 신규 SQL 회귀와 기존 배포·검토 중·조건 응답 SQL 3개, 대기 없음 확인도 통과했으며 운영 가이드 함수는 보존했다. 보안 advisor는 기존 경고 4개로 동일하고 새 경고는 없다. 로컬 DB 엔진이 없어 로컬 migration 적용·SQL 회귀는 미실행이다. 실제 브라우저 검증과 앱 배포 확인은 하지 않았다. 적용 기록과 앱 배포·기능 확인 순서는 [운영 안내](operations.md#표형-응답-제작-2026-10-11)를 따른다.

### 흐름표의 중간 시기 추가 (2026-10-13)

제작자는 `시기 이름 설정`의 `시기 추가 허용`에서 어느 기본 시기 다음에 응답자가 시기를 추가할 수 있는지 정한다. 응답자는 시기 사이의 좁은 추가 칸에서 + 버튼을 눌러 새 시기를 넣고 이름을 직접 입력한다. 추가 칸은 폭 48px의 옅은 회청색 셀 한 개로 시기 머리글과 모든 답변 행을 세로로 합치며, 이미 추가한 시기들이 있으면 그 뒤와 다음 기본 시기 사이에 표시한다. 기본 시기와 추가 시기를 합쳐 최대 20개까지 작성하며, 기본 시기가 20개이면 추가를 허용할 수 없다. 추가한 시기는 이름 수정·삭제가 가능하고 답변이 있으면 삭제 전에 확인한다. 기본 시기의 순서·ID와 기존 답변은 추가·삭제로 바뀌지 않는다.

추가 위치는 API의 `flowInsertAfter`와 DB의 `questions.flow_insert_after`에 기본 시기의 1부터 시작하는 번호 배열로 저장한다. `maxRows`는 기본 시기 수로 유지하며, 단일 행 흐름표도 기본 시기 1개 뒤에 추가할 수 있다. 추가 시기의 이름은 최대 100자이고 임시 저장에서는 비워 둘 수 있지만, 답변을 작성한 추가 시기는 제출 전에 이름이 필요하다. 이름만 입력한 시기는 최소 작성 수에 포함하지 않는다. 저장·재열기·제출 내용·가이드 답변에서도 추가 시기의 위치와 이름을 유지한다.

제작자가 추가 허용을 해제해도 이미 저장된 추가 시기는 편집·삭제할 수 있으며 그 위치에 새 시기를 넣는 것은 차단한다. 기존 시기 정보를 저장한 원본은 기본 시기 수와 표시 방식을 바꾸지 못한다. 구형 편집기의 흐름표 내용 수정 요청에서 `flowInsertAfter`가 생략되면 기존 설정을 보존하고, 명시적 빈 배열은 허용 위치를 해제한다. 조건으로 흐름표 전체가 비활성이면 제출본에는 자리 정보만 남기며 추가 시기의 이름과 답변은 공개하지 않는다. Migration은 `20261013033907_question_flow_insertions.sql`, SQL 회귀는 `supabase/tests/question_flow_insertions.sql`이며 적용·검증 결과는 운영 안내에 기록한다.

아직 저장되지 않은 흐름표와 다른 제작자의 기본 시기 수/표 형식 변경이 충돌하면, 응답 화면은 현재 구성과 입력을 유지하고 저장을 중단한다. 안내에 따라 현재 입력을 복사한 뒤 질문지를 다시 열어 최신 구성을 사용한다. 같은 시기 수에서 이름·내용·추가 허용 위치만 바뀌는 경우에는 기존 입력을 유지하면서 최신 구성으로 계속 작성한다.

### 배포본 검토 요청 공유 (2026-10-12)

다른 컨설턴트 리드도 활성 배포 질문지에 포함된 질문의 검토 요청 전체를 읽을 수 있다. 조회 허용 범위를 확장한다. 새 요청 작성은 질문 자체의 활성 검토 중 여부로 판단한다. 배포본에만 있는 질문은 작성 불가하며, 같은 질문이 다른 활성 검토본에도 있으면 요청할 수 있다. 원본 작성자·기존 요청자·관리자의 기존 조회 범위는 유지한다.

### 제출 응답 PDF 다운로드

배포 질문지의 제출 응답 목록에서 `사람별 PDF 일괄 다운로드`를 누르면 현재 목록의 마지막 제출본을 사람마다 PDF 한 개로 만들어 ZIP으로 내려받는다. 사람별 답변 상세에서는 `PDF 다운로드`로 한 사람의 제출본을 받을 수 있다. 생성 중 진행 수와 실패 시 재시도 안내를 표시한다.

PDF에는 질문지 제목, 응답자명, 한국 시간 기준 제출일, 섹션·질문 순서와 활성 답변 행만 포함한다. 일반 표·흐름표는 긴 답변을 읽기 쉽도록 행/시기별 세로 목록으로 변환하며 기본·추가 시기 이름, 선택지명, 여러 직접 입력, 척도 점수, 서술형 강조·목록을 보존한다. 안내 카드는 응답 대상에서 제외한다. 탐구활동·학습법 참조 필드는 첨부 여부를 표시하고 상세 내용은 서비스에서 확인한다. ZIP 내부 파일명은 순번·응답자명·질문지 제목으로 구성해 동명이인도 덮어쓰지 않는다.

기존 제출 조회 API가 반환한 데이터만 사용하고 PDF 생성은 다운로드 시 브라우저에서 수행한다. API·DB 권한/스키마 변경이나 migration은 없다. 실제 브라우저 테스트 없이 `scripts/verify-submitted-response-export.mjs`, 타입 검사, 변경 파일 린트, Webpack 빌드와 가상 응답 PDF 생성·페이지 이미지 검사를 수행했다. 앱 배포 후 사용 가능하다.

### 검토 중 질문지에서 다른 작성자 원본 편집 조회

질문지의 원본 편집기는 검토 중 공동 편집 시 `questionnaireId`를 단건 질문 조회에 전달한다. 서버는 기존 `read_shared_question_sources`로 질문지 접근 권한과 실제 배치를 확인하고 해당 원본만 반환한다. 관리자의 리드 화면에서도 독립 질문 목록의 작성자 필터 때문에 타인 원본이 404로 처리되지 않는다. 독립 질문 조회·목록의 기존 필터, 원본 저장 권한·배포 잠금은 유지한다. DB migration은 없고 앱 배포가 필요하다.

질문/질문지 전환 버튼 우측 상단에는 검색 전 열람 가능한 전체 개수를 표시한다. 질문지는 보관을 제외한 수정 중·검토 중·배포 합계다. 기존 조회 API의 권한 범위를 따르며 로딩·조회 실패 시 0으로 오인하지 않도록 대시를 표시한다. 개수는 재진입·포커스 복귀·주기 조회 시 갱신한다.

### 질문 생성·편집 디자인

Drawer에 새 질문 만들기/질문 수정 제목과 안내를 표시하고 저장 행동을 상단에 유지한다. 편집·미리보기는 공통 shadcn Tabs이며 편집 내용을 마운트한 채 전환한다. 기본 정보와 질문 본문은 공통 Card의 옅은 노란 강조 머리글로 구분한다. 답변 열은 회색 머리글의 Card로 묶고 입력은 공통 Input 및 기존 회색 서식 편집기를 사용한다. 모바일 본문 여백을 줄이고 보조 설정은 같은 테두리·모서리 기준으로 정리한다. 질문지 안의 공통 질문 제작기에도 적용된다. 저장·자동 저장·조건·필수 검사·잠금·ID·API 계약 변경 없음.

편집 화면은 관리용 기본 정보를 질문 바깥에 두고, 질문 본문·설명·답변 설정을 하나의 질문 영역 안에 순서대로 배치한다. `question-styles.ts`의 questionSurfaceClass/questionPromptClass를 실제 QuestionBlockPreview와 함께 사용해 질문 번호·배치·너비·여백·테두리를 맞춘다. 입력 필드와 설정은 삭제하거나 접지 않으며 표/흐름표 및 조건 동작을 유지한다.

실제 질문지 표시 디자인: 회색 바탕에 흰 질문 영역을 배치하고 질문지 제목 아래 검정 구분선, 섹션 번호는 검정 바탕·노랑 글자, 질문 번호는 작은 노랑 표식을 사용한다. 본문 아래 구분선으로 답변 영역을 나누고 설명은 흰 배경·왼쪽 회색 선으로 표시한다. 선택 항목 배지는 무채색으로 통일한다. 공통 QuestionnairePreview/QuestionBlockPreview를 통해 미리보기와 실제 응답에 적용하며 질문·답변 내용 및 제출 계약은 변경하지 않는다.

질문 본문의 저장된 highlight 서식(예: ‘실적’ 강조)은 공통 `PencilHighlight`로 표시한다. 설명·답변 등 공통 RichTextContent 읽기 화면에도 적용하며 기존 서식 데이터와 편집기 동작은 유지한다. 섹션·질문 번호 디자인은 그대로 유지한다.

### 편집·읽기 표시 차이 정리（2026-10-14）

편집 질문 번호는 읽기 화면과 같은 questionNumberClass를 사용한다. Tiptap Highlight의 HTMLAttributes에 공통 PencilHighlight CSS와 marker 속성을 적용해 저장 데이터 형식을 바꾸지 않고 편집/읽기 강조를 동일하게 표시한다. 배포 화면의 미리보기·제출된 답변은 공통 shadcn Tabs를 사용하고 URL 선택·기존 마운트 정책을 유지한다. 모바일 질문지 바탕 여백은 8px, 질문 영역은 12px로 줄이며 sm 이상은 기존 32px/24px를 유지한다.

모바일 간격 후속 조정: 질문지 제목과 미리보기 안내를 하나의 header로 묶고 섹션 제목의 세로 여백·모바일 글자 크기를 줄였다. 질문 번호는 배경 없는 작은 숫자로 표시하고 공통 질문 카드 상단의 얇은 노란 선으로 카드 단위를 구분한다. 모바일 본문 구분선 여백과 내부 간격도 축소하며 편집·응답·안내 카드가 같은 스타일을 사용한다.

모바일 회색 문서 바탕의 안쪽 여백은 사용자 확인 후 상하좌우 16px로 조정했다(sm 이상 32px 유지). 질문 본문은 부모 Tabs의 text-sm을 상속하지 않도록 공통 questionPromptClass에 text-base(16px)를 명시한다.

일반 가이드 답변은 접기/펼치기 안에 항목별 흰 카드로 표시한다. 숫자 행 이름은 항목 N으로 표시하며 사용자 지정 이름은 유지한다. 답변 라벨과 내용은 데스크톱에서 두 열, 모바일에서는 세로로 배치하고 필드 사이 구분선을 둔다. 기존 전용 흐름표 가이드와 데이터·서식·조회 권한은 유지한다.

모바일 질문지 목록은 3열을 압축하지 않고 각 행을 2단으로 배치한다. 제목·작성자·날짜는 전체 너비, 바로가기와 상태·삭제는 아래 조작 줄에 표시한다. 모바일 열 머리글은 숨기되 데스크톱 3열과 전체 colspan=3 구조는 유지한다. 날짜는 한 덩어리로 줄바꿈하고 빈 단계의 세로 여백을 줄인다.

진로 흐름의 제출 답변은 예외적으로 기존 표 팝업에서 읽는다. 검정/노랑 열기 버튼과 읽기 전용 표를 유지하며 가이드·수정 기능은 표시하지 않는다. 나머지 질문은 펼친 항목별 표시를 사용한다.

여러 필드가 있는 제출 답변의 데스크톱 라벨 열은 최소 10rem·가용 너비의 28%로 확보하고 단어 단위 줄바꿈을 우선한다. 모바일 세로 배치는 유지한다.

제출 항목마다 외곽 테두리와 회색 머리글(진한 항목명)을 두고 항목 사이 24px 간격을 확보한다. 내부 필드 사이 구분선은 제거하고 여백으로 묶어 항목 경계를 우선한다. 실제 답변은 공통 DetailValue의 회색 배경과 여백으로 강조하며 단일 필드도 원래 라벨을 유지한다. 진로 흐름 팝업은 유지한다.

척도형 답변의 공통 읽기/요약 표시는 질문의 scaleConfig.max를 사용해 `5점 / 7점 만점`처럼 선택 점수와 만점을 함께 표시한다. 기존 점수 라벨과 추가 서술은 유지하며 제출 화면은 제출본 정의의 척도 설정을 따른다. 저장 형식 변경 없음.

제출 PDF는 화면의 질문·항목·필드 위계를 유지하되 흰 종이 바탕의 텍스트 중심으로 출력한다. 질문 위 노란 선과 항목 제목 아래 얇은 회색 선만 남기며 카드 외곽선·배경색·답변 박스는 제거한다. 필드 라벨 위·본문 아래의 세로 구조로 긴 답변이 다음 페이지에 자연스럽게 이어지게 한다. 가이드는 제외하고 참조 권장 문구·척도 만점·최종 제출 일시를 포함한다. PDF는 팝업을 지원하지 않으므로 진로 흐름 내용도 문서에 직접 출력한다. 활성 제출 행 필터와 파일명/ZIP 계약은 유지한다. 다운로드 준비/생성 진행은 고정 너비 버튼 안의 스피너와 문구로 표시하며 별도 진행 문단은 생성하지 않는다. 실패 안내는 기존 오류 영역을 사용한다.

제출된 흐름표는 표시 전에 materializeFlowRows로 구형 행의 누락된 flowIndex를 기존 순서에 따라 복원한다. 저장된 ID만 표시하여 빈 시기를 새로 추가하지 않으며, 명시적 flowIndex·추가 시기 이름·본문은 유지한다.

### 진로 흐름 입력·항목 이름 표시

진로 흐름은 계속 전용 팝업으로 작성·열람한다. 흰 팝업과 표, 회색 입력 칸, 노란 상단 선을 사용하고 필수/작성 시기 수는 공통 Badge로 표시한다. 모바일에서는 고정 항목 열을 160px, PC에서는 240px로 두고 시기 열을 가로 스크롤한다. 제출 열람에서는 입력 안내·예시·추가·삭제 조작을 숨긴다.

진로 흐름 가이드는 표시 이름으로 행을 검색하지 않고 응답 행 ID별로 직접 표시한다. 같은 이름의 항목도 각자의 답변이 보존된다. 이름 있는 비흐름표 답변은 제출 시 원래 위치의 이름을 `rows[].label`로 보존하며 화면·진로 흐름 팝업·PDF가 공통 `submittedRowLabel`을 사용한다. 구형 압축 제출본에서 이름을 확인할 수 없으면 `항목 N · 원래 이름 미확인`으로 표시한다. 숫자 행 ID를 원래 순서로 추정하지 않는다. 기존 제출본의 안전한 보정 조건은 저장 구조 문서를 따른다.

로컬 `[로컬 UI 확인] 모든 답변 유형`의 기존 첨부형 질문·가이드·제출 답변도 서술형 및 본문 참조로 전환했다. 원문 질문 제목·라벨·배치·필수 여부와 ID는 유지한다. 과거 첨부형 가이드의 링크 누락은 별도 유형을 제거하면서 해소한다. 진로 흐름 작성 시 시작 시기와 입시 결과의 기존 필수 입력 칸은 표의 필수 셀 바탕만 연노랑(brand 10%와 background를 혼합한 불투명 색)이며, 그 안의 답변 요약 버튼과 편집 입력창은 회색을 유지한다. 선택 셀 바탕은 흰색이다. 셀의 답변 영역을 한 번 누르면 편집창이 열리면서 바로 커서를 둔다. 읽기 전용에는 필수 배경을 적용하지 않는다.

### 질문지 관리 초기 로딩 정리 (2026-10-14)

| `GET /api/questions/:id` | 본인/관리자의 원본 상세. `questionnaireId`가 있으면 기존 검토본 조회 RPC가 배치·공유 열람 권한을 검사한다. |
| `GET /api/questions/:id/guide-answer-fields` | 가이드 응답이 존재하는 답변 열 ID 조회. 저장 때 DB가 다시 확인한다. |
| `POST /api/questions`, `PUT /api/questions/:id` | `document`, `expectedRevision`, `saveId`, 선택적 `confirmedGuideAnswerFields`. 생성 revision은 0이고 URL/본문 ID가 같아야 한다. |
| `DELETE /api/questions/:id` | `expectedRevision`을 확인하여 보관 처리. 기존 배치·참조·배포 잠금을 유지한다. |
| `GET /api/question-reviews?questions=id,...` | 최대 10개 질문의 미처리/미확인 개수. `question_review_counts` 한 번으로 DB에서 집계한다. |

목록의 `withQuestionnaireUsage`는 현재 페이지 ID를 `question_incoming_references`에 전달한다. 전체 질문을 앱 서버로 가져와 역참조를 계산하지 않는다. 조건 JSONB에는 GIN 인덱스를 추가하고 기존 source/after 인덱스와 함께 대상 질문으로 필터링한다. 한 질문이 선행·조건·응답 참조에 동시에 등장해도 한 번만 표시한다. 관리자 역할 미리보기에서 타인 질문 이름을 숨기는 기존 필터와 사용처 조회 실패 시 알 수 없음 처리를 유지한다. 그래프와 조건 후보의 명시적 전체 조회는 이 역참조 집계 경로와 구분한다.

두 집계 RPC는 `SECURITY INVOKER`로 기존 RLS를 적용한다. 관리자·리드만 호출하며 일반 컨설턴트·비로그인은 거절한다. 읽지 않은 요청은 원본 작성자에게만, 다른 사람이 작성한 미처리 요청 중 본인의 읽음 기록이 없는 경우에 센다. 기존 요청자·검토 중/배포본 공유 열람 정책을 유지한다. 결과는 JSONB 집계로 반환하여 Data API 1,000행 제한에 의해 개수가 잘리지 않는다.

저장 schema 오류는 HTTP 400의 `code: question_validation_failed`, `error`, `fieldErrors: [{path, message}]`로 반환한다. 예: `path: ["document", "fields", 0, "label"]`. 편집기도 동일한 오류 설명 변환을 사용하므로 기존 토스트에 항목·위치가 표시된다. 설명 ID 중복은 API와 편집기에서도 미리 거절한다. 알려진 DB 검증 오류에는 설명/조건 등 영향 영역을 반환하며, 알 수 없는 DB 오류 본문을 그대로 노출하지 않는다. `revision_conflict`, `question_edit_restricted`, `guide_answer_confirmation_required`의 기존 코드·재시도 처리는 유지한다.

### 저장 전 새 질문의 새로고침

- URL의 질문 UUID만으로 서버 저장 여부를 판단하지 않는다. 사용자 확인 후 해당 사용자의 로컬 초안 revision을 확인한 뒤 상세 조회를 시작한다.
- revision 0인 새 질문은 빈 초안도 로컬에서 복원하며 상세 API를 호출하지 않는다. 서버에 저장된 질문은 기존 상세 조회·충돌 검사 경로를 유지한다.

### 설명 항목 공통 계약 (2026-10-15)

- 설명 전용 하위 API는 만들지 않는다. 질문의 `details`로 조회·저장하고 `save_question`의 단일 트랜잭션/revision/saveId를 사용한다.
- `lib/question-details.ts`에서 `QuestionDetail`, `questionDetailSchema`, `QUESTION_DETAIL_LIMITS`(20개/제목 200자/본문 저장 문자열 10,000자)를 관리한다. 질문 제작·원본 저장 검증·질문지 현재 문서 검증이 같은 기준을 사용한다.
- `hasQuestionDetailContent`는 제목 또는 서식에서 추출한 본문에 내용이 있는지 검사한다. 질문 미리보기·질문지 배치 카드·구형 등록 안내 카드에서 완전히 빈 설명만 숨긴다. 본문만/제목만 있는 설명은 표시하며 편집기와 저장 데이터에서는 빈 항목도 보존한다. 공개 여부 필터는 별도로 그대로 적용한다.
- 질문지 `savedDraftSchema`의 구형 로컬 초안 읽기에만 기존 설명 제한(30개/500자/20,000자)과 서식 정규화를 유지한다. 현재 질문지 저장은 설명을 원본에서 수정하도록 계속 거절한다. 호환 스키마를 신규 설명 저장에 사용하지 않는다.

### 검토 요청 조회·저장 정리 (2026-10-15)

검토 요청은 별도 테이블에 저장하되 원본 질문 하나에 귀속한다. 질문지 출처는 권한·동일 요청 재시도·화면 상태에 영향을 주지 않는다. 원본 작성자 본인의 요청은 차단하며 원본 작성자·관리자의 처리 권한을 유지한다.

| API | 현행 계약 |
| --- | --- |
| `GET /api/questions/:questionId/reviews` | 미처리 요청 전체, `pendingCount`, `completedCount`, `canRequest`, `canResolve`, `unreadIds`, `page`, `hasMore` |
| 같은 GET에 `completed=true&page=N` | 완료 이력 10개씩, 동일 권한·개수 정보. `unreadIds`는 빈 배열 |
| `POST` | `{id,description}` 등록. 성공은 `{ok:true}` |
| `PATCH` | `{id}` 처리 완료. 성공은 `{ok:true}` |
| `PUT` | `{ids}` 읽음 처리, 1~100개 UUID. 성공은 `{ok:true}` |
| `GET /api/question-reviews?questions=...` | 최대 10개 질문의 미처리·미확인 집계. 기존 계약 유지 |

- 변경 API는 쓰기 성공 이후 목록/권한을 재조회하지 않는다. 클라이언트도 쓰기 성공 시 입력을 정리하고 성공을 안내한 뒤 별도로 갱신한다. 갱신 실패는 저장 실패와 구분해 안내한다. 쓰기 결과를 확인하지 못하면 내용과 동일 요청 ID를 유지한다.
- 단일 질문의 조회·생성·처리·읽음은 `/api/questions/:questionId/reviews`로 통일한다. 목록 집계는 여러 질문을 대상으로 하므로 `/api/question-reviews?questions=...`를 유지한다. 구형 `/api/question-reviews/:questionId`는 같은 핸들러를 연결하는 호환 별칭이며 구형 출처 인자는 무시한다. 재시도 키는 질문·본문으로 결정하고 화면 상태도 질문 단위다.
- 읽음은 실제 보이는 미확인 카드만 150ms 동안 모아 최대 100개씩 전송한다. 숨겨진 브라우저 탭에서는 보내지 않으며 이미 성공한 ID는 같은 화면에서 반복 전송하지 않는다. 실패한 ID는 후속 조회/화면 복귀 때 재시도한다. 목록·질문지 갱신은 일괄 처리 뒤 수행한다.
- 검토 영역은 로딩·빈 상태에도 동일한 최소 높이의 접힌 요약 줄을 유지한다. 미처리/완료 수와 새 요청 표시를 제공하고 로딩은 줄 안의 스피너로 표시한다. 사용자가 펼칠 때 흰 카드에 요청 내용을 표시한다. 자동으로 영역을 확장하지 않는다. 10초 갱신은 유지한다. 완료 요청은 접힘 영역을 펼칠 때 처음 조회하고 10개씩 `더 보기`로 추가한다. 열린 동안만 완료 이력의 주기/포커스 갱신을 수행한다. 정렬은 요청 시각 내림차순·ID 내림차순이며 겹친 페이지의 ID는 화면에서 중복 제거한다. 표시 개수는 서버 집계를 사용한다.
- 질문지 상세의 상단 미처리 수는 본문 없는 정확한 count 조회로 받는다. 종전 `reviews` 응답 필드는 호환용 빈 배열이며 개별 요청 본문은 질문별 API에서만 읽는다.

코드 책임: `lib/reviews/types.ts`는 `QuestionReview`/페이지 응답, `schema.ts`는 작업별 입력, `server.ts`는 HTTP 인증·검증·RPC 연결, `client.ts`는 URL·재시도 ID·읽음 묶음, `hooks/useQuestionReviews.ts`는 조회·완료 이력·변경 상태를 관리한다. `QuestionReviews.tsx`는 카드/접힘 영역/실제 노출 감지를 맡고 API route는 핸들러 연결만 담당한다. 기존 질문지 문맥용 wrapper는 유지한다.


### 새 질문에 내용 불러오기 (2026-10-15)

- 아직 저장되지 않은 새 질문(revision 0)의 `다른 질문 내용 가져오기`에서 기존 질문을 검색하고 10개씩 조회한다. 기존 질문 목록·상세 API와 조회 권한을 그대로 사용한다. 질문지에서 기존 원본을 배치하는 기능과는 별개다.
- 선택한 질문의 제목·본문·설명/공개 설정·답변 열/선택지/척도·표시 방식·반복 행/흐름표 시기 설정을 복사한다. 현재 새 초안 ID는 유지하며 설명·열·선택지 ID는 새로 만든다. 원본은 수정하지 않는다.
- 개인 답변·가이드 답변·검토 요청·소유자·revision·배포 잠금은 복사하지 않는다. 다른 질문을 가리키는 조건/순서/행 참조는 해제한다. 참조형 행은 단일 행으로 시작하며 조건은 새 질문에서 다시 설정한다. 폐기된 학습법 등록 안내 유형은 불러올 수 없다.
- 불러오기 창에서 기존 입력 대체를 안내하고 확인 후 적용한다. 조회 실패/취소 시 작성 내용은 유지한다. 선택 창이 열린 동안 자동 저장을 멈추며 불러온 직후의 내용을 초기 비교 기준으로 보관한다. 사용자가 이를 수정한 경우에만 기존 저장 경로로 새 질문을 저장한다. 변경하지 않거나 첫 저장 전에 불러온 내용으로 되돌리면 저장 버튼/자동 저장을 비활성화하고 닫을 때 취소 확인 없이 초안을 정리한다. 새로고침 후에도 이 비교 기준을 복원한다. 이미 자동/수동 저장된 새 질문은 이후 일반 편집 정책을 따른다. 저장 중·결과 불확실·이미 저장된 질문에는 가져오기를 허용하지 않는다.
- 공통 nested Dialog를 사용하고 편집기 본문/헤더/푸터는 inert·스크롤 잠금 상태로 둔다. `QuestionImportDialog`는 선택/조회, `copyQuestionContent`는 ID 재생성과 연결 해제, `useQuestionEditorSession`은 초안/자동 저장을 담당한다.
- 질문지 구성·기수별 공개/배포 방식 및 제출 검증은 이번 범위에서 바꾸지 않는다.


### 질문지 전체 화면 제작·질문 추가 (2026-10-15)

- 생성·수정은 전체 화면이며 `draft=new`와 저장 후 `draft=<UUID>`를 유지한다. 이전 `questionnaireEditor=drawer`는 제거하고 같은 질문지를 전체 화면으로 연다. 목록 복귀 시 검색·상태·작성자·페이지 조건을 보존한다.
- 회색 캔버스·흰 accent 카드·공통 Tabs/Label과 하단 저장/닫기를 유지한다. 미저장 이탈은 공통 AlertDialog로 확인하며 질문 편집 중에는 부모 질문지를 닫지 않는다.
- `질문 추가하기`는 옅은 회색 배경·점선 테두리의 전체 너비 버튼으로 표시하며 공통 Dialog의 기존 질문 선택 목록을 연다. 선택 즉시 원본을 배치하며 조건/참조에 필요한 선행 질문 배치 규칙을 유지한다. 이미 배치된 질문은 중복 선택할 수 없다.
- 선택 팝업의 `새 질문 만들기`는 팝업을 닫고 공통 질문 편집 Drawer로 전환한다. 배치된 질문의 수정도 같은 Drawer를 사용한다. 두 화면을 겹쳐 열지 않는다.
- 새 질문의 `다른 질문 내용 가져오기`는 독립 복사 기능이다. 질문지에서 원본을 선택해 연결하는 기능과 구분하며, 복사 후 실제 수정 전 저장 금지는 유지한다.
- 새로고침은 서버 저장분을 복원한다. 미저장 입력에 새 로컬 저장소는 추가하지 않는다. 데이터·API·권한 변경 없음.

- 기존 질문 선택 팝업은 화면 높이 안에서 헤더·새 질문 버튼·검색창을 유지하고 질문 목록만 스크롤한다. 중복된 내부 카드 테두리를 제거하며 긴 질문도 팝업 폭을 늘리지 않는다. 공통 Dialog의 열 최소 폭은 0으로 제한한다.

### 질문 추가 선택 표 (2026-10-15)

- 기존 질문 추가 팝업은 질문 관리의 `QuestionManagementTable`을 선택 모드로 재사용한다. 질문명·본문·참조/사용 정보를 유지하고 관리/검토 요청 대신 추가 버튼을 표시한다. 행 클릭과 추가 버튼은 같은 동작이며 이미 배치된 질문은 추가됨으로 비활성화한다.
- 검색 결과를 10개씩 표시하고 공통 페이지 이동을 하단에 유지한다. 검색 시 첫 페이지로 이동하고 목록만 스크롤한다. 선택 표는 질문 목록과 동일한 `useQuestionLibraryList`의 서버 검색·10개 페이지 조회를 사용하여 참조/사용 정보를 함께 표시한다. 제작기의 전체 질문 데이터는 참조 검증·선행 질문 배치용으로 별도 유지한다. 서버 API·권한·원본 배치 계약은 변경하지 않는다.

- 질문지의 공통 질문 편집 Drawer는 루트를 유지하고 open 상태를 전환하여 열기·닫기 애니메이션을 적용한다. 닫힌 편집기는 마운트하지 않아 자동 저장을 실행하지 않는다.

- 질문 배치 카드는 실제 질문 본문을 강조하고 공통 설명 스타일을 사용한다. 관리용 이름 중복·최대 행 수는 표시하지 않으며 답변 열 이름/유형만 간단히 요약한다. 전체 입력 영역은 미리보기에서 확인한다.

- 시작 안내의 `탐구활동 등록 버튼 표시`는 학습법 버튼과 독립적으로 켜고 끌 수 있으며 문구를 편집한다. 클릭 시 기존 탐구활동 작성 Drawer를 열고 안내 등록을 강제하지 않는다.

- 시작 안내의 학습법·탐구활동 등록 버튼은 공통 Button의 wrap 크기(최소 높이 40px·동일 여백·긴 문구 줄바꿈)를 사용한다. 로딩 중 버튼에도 같은 크기를 적용한다.

### 기본 비공개 질문·질문지 초안 권한 (2026-10-15)

- 별도 검토 중/배포가 없는 독립 질문은 작성자·관리자만 조회/수정한다. 기존 질문 정책을 유지한다.
- 수정 중인 질문지는 작성자·관리자만 조회/수정한다. questions와 달랐던 questionnaires SELECT RLS를 제한하며 하위 섹션·질문 배치는 부모 RLS를 따른다. 관리자 초안 조회/저장 RPC 및 안내 편집을 허용한다.
- 서버 목록/상세와 공통 목록 모델은 관리자 초안을 표시한다. canEditDraft는 편집 권한 표시이며 isOwner는 실제 소유권으로 유지한다. 내 질문지 필터나 검토 중·배포 권한을 관리자 소유로 위장하지 않는다.
- 검토 중/배포/보관 정책은 이번 변경에서 확대하지 않는다. 기존 데이터·ID·revision과 함수 ACL은 유지한다. migration은 기존 권한 정의가 예상과 다르면 중단한다.


## 질문지 상태 명칭과 API 전환 (2026-10-15)

수정 중은 `draft`, 검토 중은 `in_review`, 배포는 `published`다. 검토 중 진입은 원본 질문까지 공유한다. 질문지와 원본의 권한·수정 잠금·가이드·제출 동작은 그대로 유지한다. 상태 색상과 전체 목록 최대 2/2/10개도 유지한다.

목록 응답의 그룹은 `drafts`, `inReview`, `published`, `archived`이고 상세 공용 조회는 `sharedDocument`, `sharedSources`다. 검토 시작 시각은 `reviewStartedAt`, 배포 시각은 `publishedAt`이다. `ReviewResponse`는 가이드/검토 응답, `SharedQuestionnaire`는 공유 질문지, `QuestionResponseForm`의 published 옵션은 배포 응답을 의미한다.

- `POST /api/questionnaires/:id/review`: 검토 시작.
- `POST /api/questionnaires/:id/publication`: 배포. 미처리 검토·소유권·revision 검사 유지.
- `PATCH /api/questionnaires/:id/status`: `{status,expectedStatus,revision,archivedAt,requestId}`. 상태는 새 명칭만 허용한다.
- `GET/POST/PUT /api/questionnaires/:id/review-responses`: 가이드 작성/검토 세션.
- `GET/POST/PUT /api/questionnaires/:id/published-responses`: 배포 응답 세션.
- 질문지 API의 모든 요청에 `X-Questionnaire-Workflow: 2`가 필요하다. 이전 화면은 426과 새로고침 안내를 받고, 변경된 상태 의미로 읽거나 저장하지 못한다. 새 클라이언트는 426을 자동 재시도하지 않는다.

새 목록 링크는 `qStage`를 사용한다. 과거 `qStatus=published`는 검토 중, `qStatus=distributed`는 배포로 읽으며 검색·작성자·페이지·상세 ID는 유지한다. 두 값이 함께 있으면 qStage가 우선한다. 상태 필터를 변경하면 qStatus를 제거한다. 응답 본문과 질문 로컬 초안은 이름 변경 때문에 삭제하지 않는다.

과거 migration 이름과 이전 작업 기록의 published는 그 당시의 검토 단계를 뜻한다. 현행 코드/API와 혼용하지 않는다. 전환·구형 RPC 차단·적용 순서는 운영 문서의 최신 절을 따른다.


## 응답 무결성과 조회 구조 (2026-10-15)

질문지 전체 저장·제출, 자동 저장 10초·가이드 동기화 5초, 충돌 시 입력 보존, 재제출, 현재 화면·PDF 디자인과 배포 권한은 유지한다. 질문별 오류 위치 안내는 아래 제출 전 오류 안내 절을 따른다.

- 정의 변경과 다른 탭의 답변 저장이 동시에 도착하면, 미수정 화면은 최신 서버 답변을 채택한다. 미저장 입력이 있는 화면은 입력을 보존하고 저장을 잠근다. 정의만 바뀌었으면 기존과 같이 호환 필드를 유지한다. 다른 세션/질문지로 이동할 때 편집 상태를 새로 초기화한다.
- `QuestionResponseForm`은 로딩·화면을, `hooks/responses/useQuestionResponseEditor`는 편집·저장·재시도·원격 반영을 담당한다. `lib/responses/api-client`는 HTTP, `schema`는 요청 검증, `requirements`는 질문의 필수 시기 검사를 담당한다. 서버 명령과 제출 조회는 `question-response-server`·`responses/submissions-server`로 분리한다.
- 제출 목록은 서버에서 10명씩 이름·최종 제출 시각·제출 revision만 읽는다. 공통 페이지 이동 UI를 사용하며 상세에서 목록으로 돌아오면 직전 페이지를 유지한다. 한 사람을 선택한 때만 제출 답변과 질문 정의를 조회한다. 다른 응답자로 이동할 때 이전 사람의 답변을 임시 표시하지 않는다.
- 전체 PDF는 다운로드 시작 시 제출 ID/revision 목록을 한 번 읽고, 한 사람씩 상세 조회→PDF 생성한다. 조회 전에 재제출되어 revision이 다르면 전체 ZIP 생성을 중단하고 재시도를 요청한다. 부분 ZIP을 내려받지 않는다. 버튼 안 진행 표시·PDF 레이아웃은 유지한다. ZIP 결과 파일 자체는 브라우저 메모리에 모으므로 매우 큰 내보내기의 서버 작업 전환은 별도 과제다.
- 배포 질문지 조회·응답 대상은 기존 역할 정책 그대로다. 작업 답변은 본인 전용이고 리드·관리자의 제출 조회는 최종 제출본만 반환한다. 가이드 지정 계정과 배포 잠금도 바꾸지 않는다.


## 제출 전 오류 안내와 질문 이동 (2026-10-15)

제출은 계속 질문지 전체 단위다. 제출 버튼을 누르면 `validateResponseSubmission`이 현재 배치 순서대로 각 질문의 `validateQuestionSubmission` 결과를 모은다. 필수 열·최소 항목/시기 수·선택형 직접 입력 미완성·척도 범위·추가 시기의 이름·진로 흐름 필수 시기를 검사한다. 표의 완전히 빈 여분 행과 조건상 비활성 질문은 완료 검사에서 제외하며, 숨겨진 질문에 보존된 답변이 다음 질문의 조건을 활성화하지 않도록 활성 답변만 전달한다.

오류가 있으면 제출 요청을 보내지 않고 상단에 문제가 있는 질문 목록을 표시한다. 첫 오류 질문으로 자동 스크롤하고 키보드 포커스를 이동한다. 목록 버튼은 해당 섹션·질문으로 다시 이동한다. 해당 질문은 기존 노란 상단 테두리를 유지하며, 질문 제목 아래 카드 안에 옅은 오류 배경의 안내를 표시한다. 아이콘·짧은 제목과 항목/열 이름을 포함한 본문을 구분하고 카드 전체를 빨간 테두리로 감싸지 않는다. 접힌 항목이나 진로 흐름 팝업을 임의로 열지는 않으며 질문 위치에서 오류에 표시된 항목을 확인할 수 있다. 시스템의 동작 줄이기 설정에서는 스크롤 애니메이션을 생략한다.

한 번 제출 검사를 한 뒤에는 입력 변경에 따라 해결된 오류를 바로 제거한다. 이 오류 때문에 편집이나 임시 저장을 잠그지 않는다. 모든 오류가 해결된 뒤 다시 제출하면 기존 질문지 전체 제출 요청을 보낸다. 제출 성공 전에는 기존 최종 제출본이 유지된다. 서버의 권한·동시 수정·최종 완료 검사는 계속 적용하며 네트워크/권한/충돌 오류는 기존 별도 안내를 유지한다.

추가 DB/API 계약 변경은 없으며 현재 서버 규칙을 변경하지 않는다. 화면, 순수 검증 함수, 스크롤/포커스 유틸리티를 분리한다. 저장된 과거 선택형·척도형의 추가 서술 허용 옵션도 검증과 조건 판정에서 보존한다.


## 목록 조회 및 답변 판정 개선 (2026-10-15)

- 검색·상태·작성자·페이지 URL을 서버 요청과 캐시 키에 반영하며 상세를 닫으면 기존 목록 조건으로 돌아온다. 새 조건을 불러올 때 이전 조건의 행을 새 결과처럼 표시하지 않고 기존 표 안의 스켈레톤을 사용한다. 실패는 재시도할 수 있다.
- 제출 전/완료 탭은 동일한 카드 목록과 상태 문구를 유지하며 서버 페이지와 전체 수를 사용한다. 제출 상태도 현재 페이지의 개인 상태만 받는다.

## 응답 화면 백그라운드 조회 (2026-10-16)

디자인·입력·제출 UI는 유지한다. 자동 저장은 기존 10초 주기를 유지하며 숨겨진 탭에서도 기존 저장 동작을 유지한다. 원격 변경 확인은 화면이 보일 때 30초마다 수행하고 focus/visibility 복귀 때 즉시 확인한다. 숨겨진 탭에서는 원격 조회를 시작하지 않고 진행 중인 조회 결과도 적용하지 않는다. 변경이 없으면 입력칸·펼침 상태를 다시 설정하지 않는다. 같은 요청이 겹치지 않으며 다른 탭 수정의 미저장 충돌·정의 변경 처리는 기존 방식으로 안내한다.


### 제출된 답변 직접 진입 로딩 (2026-10-16)

질문지 목록에서 `questionnairePanel=responses`로 진입하면 질문지 메타데이터 조회 단계부터 제출 목록/상세 전용 `SubmittedResponsesLoading`을 사용한다. 부모는 탭 자리를 포함하고, 실제 탭이 준비된 뒤 답변 조회 단계에서는 동일한 본문 skeleton을 사용하여 편집기 로딩 → 질문지 로딩 문구 전환을 제거했다. 공통 Skeleton/Tabs를 사용하며 응답자 상세는 다운로드/응답자 정보 자리를 구분한다. 조회·권한·저장·URL 계약은 변경하지 않는다. main 브랜치에서 로컬 수정하며 브라우저 테스트·운영 배포는 수행하지 않았다.


### Realtime 구독 거절 반복 방지 (2026-10-16)

운영 Unauthorized 로그의 계정은 consultant였고 본인/배포 알림 정책은 존재했다. 로그 auth_user=null만으로 토큰 누락을 확정하지 않는다. 질문지 구독은 로컬 세션의 계정 일치 확인과 realtime.setAuth 완료 후 시작하도록 보완했다. CHANNEL_ERROR의 명시적인 Unauthorized/permissions/forbidden은 채널을 제거하여 SDK 반복 재가입을 중단한다. 기존 HTTP 주기적 조회·서버 권한·답변 저장은 유지한다. 새 페이지 진입 시 재시도하며 권한 정책은 넓히지 않는다. 운영은 읽기 전용 확인만 수행했고 실제 로그 감소 확인은 앱 배포 후 필요하다.

### 질문지 편집·미리보기 좌우 여백 (2026-10-19)

질문지 편집기 안의 미리보기는 `embedded` 표시로 문서 내부 좌우 여백을 생략하고 편집기 공통 바탕의 여백(모바일 16px, sm 이상 32px)을 한 번만 적용한다. 검토 중 가이드 답변 작성 경로도 동일하게 전달한다. 독립 질문지·응답 화면의 기존 여백과 세로 간격, 저장·권한 동작은 유지한다.

시작 안내 추가 버튼은 공통 outline Button의 흰색 기본 배경을 사용한다. 점선 테두리와 기존 추가 동작은 유지한다.

## 조회 로딩 UI (2026-10-19)

학습법·탐구활동 첨부 선택 목록은 최초 조회·검색 대기·페이지 이동 중 공통 `AttachmentListSkeleton`으로 제목/요약/상세 버튼 위치를 표시한다. 검색창과 추가·페이지 이동 영역은 유지하며 스크린리더에 로딩 상태를 알린다. 기존 검색·선택·권한·API 계약은 유지한다.
