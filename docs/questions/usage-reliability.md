# Supabase 사용량 사고와 재발 방지

질문·질문지·응답뿐 아니라 같은 인증/저장 기반을 쓰는 학습법·탐구활동 작업에도 적용한다. 현행 데이터 계약은 [data-api.md](data-api.md), 실행 명령과 환경별 적용 이력은 [operations.md](operations.md)를 따른다.

## 2026-10-16 확인한 두 문제

| 문제 | 확인된 사실 | 대응 상태 |
| --- | --- | --- |
| 로그 폭증 | PostgREST 14.5에서 업무 충돌을 SQLSTATE40001로 발생시켜 서버 내부 재시도가 지속됨. 사용자 첨부 시점 Log Ingestion 71.43GB/1GB | 문제 연결 종료 및 함수 15개 오류 전달 변경을 운영 적용. 짧은 구간에서 관련 호출 약522회/초→39초간3회 확인 |
| Egress 증가 | 첨부 시점5.83GB/5GB. 10월11일 PostgREST 약869MB, Auth 약317MB. 전체 답변5초조회 및 동일 요청의 중복 인증/프로필 조회 확인 | 메타데이터 확인·30초 조회·숨김 중지·인증 재사용을 로컬 구현/검증. 운영 배포 대기 |

두 지표의 전부가 같은 원인이라고 단정하지 않는다. 최종 제출 시각 기준 11일7명·12일15명이지만 동시 접속 기록이 아니다. 당시 Egress 중 각 코드 경로의 정확한 기여율은 미확정이다. 현재 주요 JSON 약50KB를 이용한 전송 추정은 압축·브라우저 제한·실제 체류 시간을 반영하지 않은 추정치다.

인지가 늦어져 로그/사용량 누적 후 대응했다. 현재 자동 사용량 경보나 장기 관측 체계를 설치한 것은 아니므로 이를 해결 완료로 기록하지 않는다. 로그 문제의 운영 수정과 Egress 개선의 로컬 완료를 외부 지원 문의에서도 구분한다.

## 구현·검토 규칙

1. **오류 분류**: 업무 revision/save_id 충돌에 SQLSTATE40001을 쓰지 않는다. 실제 DB 오류는 PGRST, 호환 JSON code는40001, HTTP는409다. 오류를 숨기거나 충돌 검사를 제거하지 않는다. 모든 재시도는 횟수/간격/중복 저장 식별자를 검토한다.
2. **최종 DB 확인**: migration 파일 검색만으로 판단하지 않는다. 과거 파일은 구형 구문을 포함할 수 있으므로 전체 체인 이후 private 함수에 업무용 errcode40001이 남지 않는지 검사한다. 긴급 수정 후 후속 함수 재생성·정의 지문 검사·migration 이력을 함께 확인한다.
3. **반복 조회 예산**: 변경이 없을 때 응답 크기, 탭당 호출 수, 인증/프로필의 추가 호출 수를 계산한다. 세션별 조회가 다른 사용자의 전체 응답까지 가져오지 않는지 확인한다. 정기 조회에 전체 본문을 기본 반환하지 않는다.
4. **화면 수명과 경쟁**: 숨긴 탭 조회 중지, 복귀 확인, in-flight 중복 방지, GET timeout, unmount 후 결과 무시를 적용한다. 저장 중 시작/종료한 조회가 새 입력을 덮어쓰지 않는지 검증한다. 자동 저장을 조회 최적화와 함께 멈추지 않는다.
5. **변경 감지 범위**: revision뿐 아니라 정의 token, 제출 상태/시각, 삭제 상태, 안내 변경도 감지한다. 검토 배치 변경과 미저장 병합/충돌 동작을 보존한다.
6. **권한과 세션**: 요청 범위 내 서버 검증 결과만 재사용한다. Proxy 검증을 줄인 경로의 Route Handler에서 실제 인증·온보딩·역할·표시 역할과 DB 소유권이 유지되고 갱신 쿠키를 쓸 수 있는지 확인한다. 전역 사용자 캐시와 클라이언트 주장 기반 우회는 금지한다.

현재 버전 조회는 기존 read RPC를 내부 호출하므로 DB 내부 스냅샷 계산은 남는다. Egress 절감과 DB CPU 절감을 동일한 성과로 보고하지 않는다.

## 필수 검증

- `supabase/tests/business_conflict_transport.sql`: 충돌이 즉시 반환되고 저장 내용이 보존되는지 및 최종 DB 업무 SQLSTATE40001 잔존 검사.
- `scripts/verify-response-polling.mjs`: 변경 없음, 정의 변경, 숨김/저장 경쟁, 오래된 결과, 제출/안내 변경.
- `supabase/tests/response_integrity_and_submission_reads.sql`, `supabase/tests/review_live_layout.sql`: 저장·제출본·배치 변경·권한 및 버전 조회 계약. 로컬 가상 데이터 전체 롤백.
- 타입 검사·변경 파일 린트·보안 advisor. 실제 브라우저 검증은 별도 사용자 요청이 있을 때만 한다.
- 새 반복 요청의 응답 크기·호출 빈도를 기록한다. 운영 데이터 초기화나 실제 답변 수정으로 검증하지 않는다.

## 운영 점검 절차

배포/마감일 전 담당자가 사용량 잔여량과 정상 시간당 증가율을 기록한다. 배포 직후와 다음 사용 집중 구간에 동일 지표를 비교한다. 로그와 Egress가 집계되는 시간 지연도 함께 기록한다.

- 로그: 오류 메시지·SQLSTATE·분당 횟수·PID·실제 backend_start. 같은 오류가 계속 발생하거나 호출 증가가 사용 패턴과 맞지 않으면 즉시 원인을 확인한다.
- Egress: Auth/PostgREST/Storage/Realtime/Pooler별 증가량, API Gateway Top Paths·요청 횟수·오류율·응답 크기. 누적 pg_stat_statements 수치를 특정 날짜 사용량으로 해석하지 않는다.
- 종료 조치: 반복 실행 연결임을 확인하고 PID뿐 아니라 사용자/application_name/정확한 시작 시각까지 대조한다. 일반 사용자 연결 전체를 종료하거나 로그를 꺼서 증상만 숨기지 않는다.
- 복구 확인: 문제 연결 없음, 오류 증가 중단, 기존 저장·충돌 처리 유지 확인. 짧은 확인 구간과 이후 장기 관측 결과를 분리한다. 원래 실패했던 미저장 입력이 복구됐다고 추정하지 않는다.
- 지원 문의: 첨부 시점 사용량·프로젝트·발생/조치 시각·실제 적용 범위를 제공한다. 누적 사용량 초기화, 과금 면제, 유예 또는 제한 해제를 임의로 약속하지 않고 지원팀에 확인한다.

**후속 운영 과제(미구현)**: 사용량/오류 증가 경보 채널·담당자·예산 기준 설정, 정기 관측 자동화, 배포 후 Egress 감소 측정. 자동 경보가 구축되기 전에는 위 수동 점검이 필요하다. 임의의 자동화나 지원 메시지 발송은 이 문서 작성으로 실행되지 않는다.


### 긴급 함수 수정 후 후속 migration 검증

운영 긴급 수정이 pending migration보다 먼저 적용된 경우, 정상 기준 스키마뿐 아니라 긴급 수정이 선적용된 스키마에서 **남은 전체 체인**을 검증한다. 중간 migration의 함수 지문은 확인된 원본/긴급 수정본만 허용하며 검사를 제거하지 않는다. 후속 함수 재생성으로 retryable 40001이 되살아날 수 있으므로 최종 체인 완료 후 전체 함수를 재검사한다. 동일 트랜잭션 fixture의 now()는 고정되므로 데이터 보존 테스트에 과거 수정 시각을 가진 행도 포함한다.


### Realtime 구독 거절 반복 방지 (2026-10-16)

운영 Unauthorized 로그의 계정은 consultant였고 본인/배포 알림 정책은 존재했다. 로그 auth_user=null만으로 토큰 누락을 확정하지 않는다. 질문지 구독은 로컬 세션의 계정 일치 확인과 realtime.setAuth 완료 후 시작하도록 보완했다. CHANNEL_ERROR의 명시적인 Unauthorized/permissions/forbidden은 채널을 제거하여 SDK 반복 재가입을 중단한다. 기존 HTTP 주기적 조회·서버 권한·답변 저장은 유지한다. 새 페이지 진입 시 재시도하며 권한 정책은 넓히지 않는다. 운영은 읽기 전용 확인만 수행했고 실제 로그 감소 확인은 앱 배포 후 필요하다.


### 2026-10-17 재점검으로 확인한 현재 상태

운영 이력에 충돌 수정·응답 버전 조회 migration이 모두 기록됐고, 버전 조회 API의 실제 HTTP200 호출을 확인했다. 따라서 위의 10월 16일 로컬/배포 대기 표시는 당시 상태다. 현재 함수에서 업무용 retryable SQLSTATE40001은 0개이며 과거 문제 연결도 없다. 상세 증거와 관측 한계는 [운영 재점검](operations.md#2026-10-17-사용량-사고-재점검-운영-읽기-전용)에 기록한다.

응답 편집기의 버전 조회와 별개로 상위 질문지 상세는 아직 5초마다 전체 본문/공유 원본을 가져온다. 인증 중복도 해당 경로에 남는다. Egress 전체 해결로 간주하지 않으며 실제 전송 바이트와 장기 증가율 확인이 필요하다.

Log Query 조사에는 시간 범위와 source를 먼저 제한하고 동일 구간 반복 조회를 피한다. 반환 행 LIMIT는 스캔 바이트 제한이 아니다. 로그 수집 폭증 후 장애 조사로 Log Query까지 증가할 수 있으나, 조회 주체/사용량 증거 없이 사용자 또는 에이전트의 기여율을 확정하지 않는다. 청구용 일별 수치와 장기 감소 여부는 별도로 확인한다.
