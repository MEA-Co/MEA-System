# 질문 목록 서버 검색·페이지네이션

질문 테이블은 `GET /api/questions?page=1&search=검색어`로 서버에서 20개씩 조회한다. 응답의 `total`은 검색 결과 전체 수이며 `page`는 실제 조회한 페이지다. 마지막 항목이 보관되어 요청 페이지가 사라지면 마지막 유효 페이지로 보정한다. 결과가 없을 때는 1페이지/0개다.

검색은 관리용 이름(title)과 질문 본문(prompt)의 표시 텍스트를 대상으로 한다. 앞뒤 공백을 제거한 검색어 전체가 포함되는지 대소문자를 구분하지 않고 검사한다. 한글 부분 검색을 지원하지만 초성·오타 보정·형태소 검색은 아니다. 여러 단어를 입력하면 입력한 문구 그대로 검색한다. `%`, `_`, 역슬래시는 와일드카드로 해석하지 않는다. 설명·답변 열 이름·선택지는 검색 대상에 포함하지 않는다.

본문의 목록·강조 등 RichText JSON에서 텍스트를 추출해 `questions.search_text` 저장 생성 열에 이름과 함께 저장한다. 서식 때문에 텍스트 노드가 나뉘어도 같은 문장으로 검색된다. 기존 질문에도 자동 계산되며 이름·본문 수정 시 DB가 재계산한다. 원문은 변경하지 않는다. 활성 질문 전용 trigram GIN 검색 인덱스와 `(updated_at desc, id desc)` 페이지 정렬 인덱스를 사용한다. 조회 RPC는 security invoker로 기존 RLS를 따른다.

클라이언트는 입력 후 300ms 디바운스를 적용하고 검색어를 바꾸면 첫 페이지로 이동한다. 지난 요청의 늦은 응답은 적용하지 않는다. 테이블 행의 조건 설명에 필요한 직접 참조 질문만 `references`로 함께 받는다. 목록 조회에는 설명 내용과 내부 저장 해시를 포함하지 않는다.

그래프·질문 편집의 조건 설정·질문지 배치는 전체 관계가 필요해 기존 전체 조회를 사용한다. 테이블 화면에서는 이 조회를 실행하지 않는다. 전체 조회는 서버에서 500개 단위로 읽어 기본 API 행 수 제한으로 질문이 누락되지 않도록 한다. 그래프 검색은 기존 클라이언트 필터를 유지한다.

운영 반영은 `20260928052431_question_server_pagination.sql`을 먼저 적용하고 앱을 배포한다. 운영 DB에는 아직 적용하지 않았다. 새 함수가 없는 DB에서는 목록 오류가 표시되며, 전체 조회로 조용히 대체하지 않는다.

검증: `supabase/tests/question_server_pagination.sql`(45개 질문·서식/특수문자·정렬·참조·보관·권한), `scripts/verify-question-pagination-api.mjs`(조회 분리·입력 검증·권한·오류·1,001개 전체 조회). 브라우저 테스트는 수행하지 않았다.
