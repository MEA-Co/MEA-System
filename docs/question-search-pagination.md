# 질문 목록 서버 검색·페이지네이션

질문 테이블은 `GET /api/questions?page=1&search=검색어`로 서버에서 10개씩 조회한다. 응답의 `total`은 검색 결과 전체 수이며 `page`는 실제 조회한 페이지다. 마지막 항목이 보관되어 요청 페이지가 사라지면 마지막 유효 페이지로 보정한다. 결과가 없을 때는 1페이지/0개다.

검색은 관리용 이름(title)과 질문 본문(prompt)의 표시 텍스트를 대상으로 한다. 앞뒤 공백을 제거한 검색어 전체가 포함되는지 대소문자를 구분하지 않고 검사한다. 한글 부분 검색을 지원하지만 초성·오타 보정·형태소 검색은 아니다. 여러 단어를 입력하면 입력한 문구 그대로 검색한다. `%`, `_`, 역슬래시는 와일드카드로 해석하지 않는다. 설명·답변 열 이름·선택지는 검색 대상에 포함하지 않는다.

본문의 목록·강조 등 RichText JSON에서 텍스트를 추출해 `questions.search_text` 저장 생성 열에 이름과 함께 저장한다. 서식 때문에 텍스트 노드가 나뉘어도 같은 문장으로 검색된다. 기존 질문에도 자동 계산되며 이름·본문 수정 시 DB가 재계산한다. 원문은 변경하지 않는다. 활성 질문 전용 trigram GIN 검색 인덱스와 `(updated_at desc, id desc)` 페이지 정렬 인덱스를 사용한다. 조회 RPC는 security invoker로 기존 RLS를 따른다.

클라이언트는 입력 후 300ms 디바운스를 적용하고 검색어를 바꾸면 첫 페이지로 이동한다. 지난 요청의 늦은 응답은 적용하지 않는다. 테이블 행의 조건 설명에 필요한 직접 참조 질문만 `references`로 함께 받는다. 목록 조회에는 설명 내용과 내부 저장 해시를 포함하지 않는다.

그래프·질문지 배치는 전체 관계가 필요해 기존 전체 조회를 사용한다. 테이블 화면에서는 이 조회를 실행하지 않는다. 전체 조회는 서버에서 500개 단위로 읽어 기본 API 행 수 제한으로 질문이 누락되지 않도록 한다. 그래프 검색은 기존 클라이언트 필터를 유지한다.

운영 반영은 `20260928052431_question_server_pagination.sql`을 먼저 적용하고 앱을 배포한다. 운영 DB에는 아직 적용하지 않았다. 새 함수가 없는 DB에서는 목록 오류가 표시되며, 전체 조회로 조용히 대체하지 않는다.

검증: `supabase/tests/question_server_pagination.sql`(45개 질문·서식/특수문자·정렬·참조·보관·권한), `scripts/verify-question-pagination-api.mjs`(조회 분리·입력 검증·권한·오류·1,001개 전체 조회). 브라우저 테스트는 수행하지 않았다.

## 질문 제작 Drawer

질문 생성·수정은 목록 위의 Drawer에서 진행한다. PC는 넓은 오른쪽 패널, 모바일은 전체 높이를 사용한다. 목록을 유지하므로 검색어·페이지·스크롤을 보존하며, question URL 매개변수로 직접 열기와 뒤로가기를 지원한다. 화면의 제작/수정 제목과 설명은 제거하고 접근성용 제목만 숨겨 제공한다.

기존 질문은 GET /api/questions/:id로 설명을 포함한 상세를 조회한다. 조건·미리보기의 참조 데이터는 GET /api/questions?mode=relationships로 별도 조회하고 SWR 캐시를 재사용한다. 관계 조회는 설명과 내부 저장 메타데이터를 제외하며 500개 단위 서버 조회를 유지한다. 관계 데이터는 여전히 전체 질문 정의를 읽으므로 규모가 커지면 별도 최적화가 필요하다.

저장 후 목록과 상세·관계 캐시를 갱신한다. 기존 10초 자동 저장·충돌 검사·로컬 복구를 유지하고, 닫기·바깥 클릭·Escape·뒤로가기에서 미저장 내용 확인을 제공한다. 저장 중에는 닫기를 막는다. 이 변경에는 DB migration이 필요하지 않다.

검증: scripts/verify-question-drawer.mjs (브라우저 없이 상태·URL·목록 유지·미저장 닫기), scripts/verify-question-pagination-api.mjs (관계 조회의 설명 제외 포함).

## 페이지당 10개 변경 (2026-09-28)

추가 migration: `20260928055251_question_page_size_ten.sql`. 기존 검색·RLS·정렬은 유지하고 페이지 크기·offset·마지막 페이지 계산을 10개로 변경한다. 로컬 함수 적용과 SQL 회귀 검증 완료. 운영에는 아직 적용하지 않았다.

운영 적용 순서 (프로젝트 루트, 기존 migration 이력이 일치하는지 먼저 확인):

1. `npx supabase migration list --linked`로 기존 로컬/운영 이력을 비교한다.
2. `npx supabase db push --linked --dry-run --skip-vault`으로 적용 대상을 확인한다. 이전 배포가 모두 완료되었다면 이번 파일 한 개만 나와야 한다. 다른 항목이나 이력 차이가 있으면 적용 전에 확인한다.
3. `npx supabase db push --linked --skip-vault`으로 적용한다.
4. `npx supabase migration list --linked`로 이번 버전이 양쪽에 있는지 확인한다.
5. 앱을 배포하고 질문 검색·다음 페이지가 최대 10개씩 표시되는지 확인한다. DB와 앱을 연이어 반영한다.

새 질문은 최초 문서와 비교해 변경 여부를 판정한다. 아무것도 바꾸지 않았다면 저장 버튼을 비활성화하고 확인 없이 닫는다. 변경했다면 닫기 확인을 표시하고, 본문이 비어 있으면 저장 불가 사유를 안내한다. 본문 없는 수동 저장은 토스트로 차단하며 미완성 질문의 서버 저장 금지는 유지한다. 자동 저장 실패도 토스트로 알리되 같은 오류의 반복 자동 알림은 억제한다.


## 작성자별 질문 공개 범위

`20260928061511_question_creator_visibility.sql`은 리드에게 본인이 만든 질문만, 실제 관리자에게 전체 질문을 허용한다. 질문과 설명의 RLS로 전체 목록·페이지 검색·상세·관계 조회를 동일하게 제한한다. 관리자 테이블에는 현재 프로필 이름을 제작자로 표시한다. 프로필 이름이 비어 있으면 이름 없음으로 표시한다. 기존 관리자 수정 권한과 revision 충돌 차단은 유지한다.

다른 작성자의 질문 ID를 지정해 참조하거나 질문지로 복사하는 저장 경로도 트리거로 차단한다. 기존 데이터는 삭제하거나 재작성하지 않는다. 이미 질문지에 복사된 본문의 공개 범위는 질문지 권한을 그대로 따른다. 과거에 작성자 간 참조가 있다면 리드 화면의 참조 후보에서는 숨겨지며, 수정 시 본인 질문으로 정리해야 한다.

로컬 DB 적용·작성자 분리/관리자 이름/설명/검색/배치 우회 차단 SQL 검증과 보안 advisor를 통과했다. 운영에는 미적용이다.

운영 적용 순서:
1. `npx supabase migration list --linked`로 기존 이력이 일치하는지 확인한다.
2. `npx supabase db push --linked --dry-run --skip-vault`으로 대상을 확인한다. 이전 변경을 모두 적용했다면 이번 파일만 나와야 한다.
3. 예상한 파일만 있으면 `npx supabase db push --linked --skip-vault`로 적용한다. 다른 미적용 파일이나 이력 차이는 먼저 확인한다.
4. `npx supabase migration list --linked`로 이력을 확인하고 앱을 배포한다.
5. 리드 계정에서 본인 질문만, 관리자 계정에서 전체 질문과 제작자 이름이 보이는지 확인한다.

관리자 리드 미리보기에서는 GET API가 표시 역할 쿠키를 확인해 본인 created_by로 추가 필터링한다. 페이지 검색은 count/range 전에 필터를 적용하고 직접 참조도 본인 질문만 반환한다. 전체 목록·관계 후보·상세에도 동일한 필터를 사용한다. 관리자 실제 권한과 쓰기 권한은 변경하지 않는다. 이 미리보기 변경은 migration 없이 앱 배포로 적용한다.
