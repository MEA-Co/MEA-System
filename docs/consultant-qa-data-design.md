# 컨설턴트 질문–답변 자료와 질문지 확장 설계안

작성일: 2026-09-23. 상태: **설계 제안, 미구현**. DB와 애플리케이션은 변경하지 않았다. 현재 구현 설명은 [질문지 저장 설계](questionnaire-storage-design.md)를 참고한다.

같은 날 로컬 DB를 읽기 전용으로 점검한 결과 질문지 관련 테이블은 public 9개와 private 1개였고, 질문지 1개·질문 4개·응답 및 답변 0개였다. 운영 DB는 조회하지 않았다. 아래는 구조 검토 결과이며 실제 답변 품질이나 성능을 검증한 결과는 아니다.

## 목적과 데이터 경계

핵심 자산은 컨설턴트별 질문–답변 텍스트 자료다. 질문지는 이를 수집하는 UX다. 수집 기록, 독립 자료, AI 파생 자료를 구분한다.

| 영역 | 관리 대상 | 변경 규칙 |
| --- | --- | --- |
| 질문지 | 질문 정의, 입력 중 답변, 조건, 제출 원본 | 작성 중 수정, 제출 원본 고정 |
| 컨설턴트 자료 | 독립 ID, 소유자, 현재 확정본, 수정 이력 | 질문지 없이 등록·수정, 수정본 추가 |
| AI 활용 | 검색 조각·임베딩, 페르소나 요약, 학습 데이터셋 | 확정된 자료 수정본에서 생성·재생성 |

출처는 연결하지만 자료가 존재하기 위해 질문지를 필수 부모로 요구하지 않는다. 질문지 보관·삭제가 독립 자료의 연쇄 삭제로 이어지면 안 된다. 제출 당시의 답변과 이후 수정한 현재 답변은 서로 다른 시점의 기록이다.

## 공통 답변 형식

답변은 **타입이 있는 열과 안정적인 ID를 가진 행 목록**으로 표현한다. 질문마다 실제 SQL 테이블을 생성하거나 모든 화면을 표로 표시한다는 의미는 아니다. 값의 구조, 행의 생성 방식, 화면 표현을 분리한다.

| 화면 유형 | 열 | 행 생성 방식 |
| --- | --- | --- |
| 서술형 | 답변(text) | 고정 1행 |
| 척도형 | 점수(scale), 선택적 이유(text) | 고정 1행 |
| 단일선택형 | 선택(single_choice), 선택적 추가 서술(text) | 고정 1행 |
| 다수선택형 | 선택(multiple_choice), 선택적 추가 서술(text) | 고정 1행 |
| 표형 | 제작자가 정한 여러 열 | 고정 행 또는 응답자가 행 추가 |
| 참조형/블록형 | 앞선 행에서 가져오는 열 + 새로 입력할 열 | 앞선 질문의 유효한 행과 대응 |

다수선택은 한 셀 안의 목록이다. 선택값마다 행을 만들거나 다른 열과 모든 조합으로 펼치지 않는다. 직접 입력 선택지는 선택지 ID에 연결된 `{id,text}` 값을 유지하고 추가 서술은 별도 열로 구분한다. 서식 문서는 텍스트 셀의 보조 표현으로 지원하며 일반 텍스트 추출을 보장한다.

질문 정의에는 다음 정보를 둔다. 필드명은 제안이다.

- `schema_version`: 공통 형식의 버전.
- `fields`: 열 ID, 라벨, 타입, 순서, 필수 여부, 길이·범위·선택지 제한. 참조 열은 원본 열 ID와 읽기 전용 표시를 정의한다.
- `row_source`: `singleton`, `fixed`, `repeatable`, `referenced`. 최소·최대 행 수, 고정 행 ID·라벨, 원본 질문·참조할 행의 조건을 포함한다.
- `presentation`: 기존 유형의 입력 프리셋, 표·카드 표시 등.
- `rules`: 적용 대상, 작성 가능, 필수 여부를 결정하는 조건.

초기 범위는 한 질문 안에서 동일한 열 정의를 공유하는 행 목록이다. 중첩 반복 그룹 등이 필요해지면 형식 버전을 확장한다. 모든 미래 유형을 억지로 평평한 표에 맞추지는 않는다.

## 저장 구조 제안

소유자·자료·수정본의 관계는 관계형 테이블에 두고, 가변적인 열 설정과 질문 하나의 답변 행들은 제한된 구조의 JSONB로 저장한다.

| 대상 | 제안 |
| --- | --- |
| `questionnaire_questions` | 공통 질문 정의 JSONB. 기존 `kind`, `options`, `scale_config` 등의 변환 규칙 필요 |
| `questionnaire_answers` | 질문별 `answer_data` JSONB, 제출 시 만든 `qa_revision_id` 연결 |
| `questionnaire_responses` | 응답 전체 revision·제출 상태 유지. 최종 참여/제외 판정과 규칙 버전 보존 |
| `consultant_qa_entries` | 독립 자료 ID, `consultant_id`, `current_revision_id`, 활성/보관·참조 확인 상태, 시각 |
| `consultant_qa_revisions` | 자료 ID·revision, `question_text`, `schema_snapshot`, `answer_data`, `context_snapshot`, `answer_text`, `text_format_version`, 수정자·시각 |
| `consultant_qa_revision_references` | 대상 수정본·행과 원본 수정본·행·열의 연결. 행 문맥/분기 문맥 등의 용도 구분 |

기본 관리 단위는 **질문 하나 + 그 질문에 대한 답변 표 전체 = 자료 한 개**다. 각 행을 별도 최상위 자료로 만들지는 않는다. 행을 수정하더라도 처음에는 질문–답변 전체의 새 수정본을 만들고, 검색 자료를 생성할 때 필요에 따라 행별로 나눈다.

초기 추가 테이블은 독립 자료, 수정본, 수정본 간 참조의 3개다. 셀별 테이블이나 조건 노드별 테이블을 먼저 만들 필요는 없다. 자료별 revision은 유일해야 하고, 현재 수정본은 반드시 해당 자료에 속해야 한다. 참조하는 두 자료의 소유자·접근 권한도 검증한다.

JSONB 내부 행 ID에는 일반적인 SQL FK를 걸 수 없다. 따라서 원본 행·열의 존재, 중복 ID, 타입, 허용된 참조 범위는 신뢰된 저장 경로에서 추가 검증한다. 관계형 수정본 FK만으로 내부 참조의 무결성이 완성되지는 않는다.

JSONB는 질문 하나의 답변 단위로 제한한다. 행 수·본문 길이·전체 바이트 수에 상한을 두고, 독립적인 행 동시 편집이나 대규모 셀 집계가 필요해지면 행 테이블 분리를 검토한다. PostgreSQL은 JSON 내부 일부를 수정하더라도 해당 DB 행 전체에 잠금을 잡는다. [PostgreSQL JSON 설계 문서](https://www.postgresql.org/docs/17/datatype-json.html#JSON-DOC-DESIGN)

### 구조 데이터와 텍스트의 일관성

사용자가 작성한 값, 질문 원문, 열·선택지 정의, 참조 맥락 스냅샷이 편집 기준이다. `answer_text`는 이들로부터 결정적인 규칙으로 생성하고 같은 수정본에 보관하는 공식 텍스트 표현이다. AI 소비자는 이 텍스트를 사용한다.

둘을 각각 자유롭게 수정하는 API는 제공하지 않는다. 자료 수정 API도 행·열의 값을 수정하고 텍스트를 함께 다시 생성한다. 단순 서술형은 일반 텍스트 편집기로 보여주면 된다. 표 구조를 버리고 자유 서술형으로 전환하는 기능은 기존 행을 참조하는 자료의 영향을 확인한 뒤 별도의 명시적인 변환으로 제공한다.

선택 점수에 라벨이 없으면 `5점 중 4점`처럼 표현하고 문구를 추측하지 않는다. 선택지·척도 라벨과 필요한 설명은 수정본에 보존한다. 표시 방식 변경만으로 내용이 바뀌었다고 판단하지 않는다. 텍스트 변환 규칙도 버전으로 추적하며 실제 AI 입력이 바뀐 경우 파생 자료를 갱신한다.

## 참조형의 동작

이번 블록형은 표형의 행 생성 방식을 `referenced`로 설정한 경우다. 표와 카드로 다르게 보여줄 수 있지만 저장 계약은 같다. 참조는 연결을 유지하는 기능이며, 한 번 복사한 후 독립적으로 편집하는 기능과 구분한다.

질문 1: 소속되었던 고등학교의 대학 진학 특징을 실적 측면에서 작성해주세요.

| 내부 행 ID | 특징 | 구체적인 설명 |
| --- | --- | --- |
| trait-a | 수시 진학 비중이 높음 | 학생부종합전형 진학 사례가 많았음 |
| trait-b | 특정 계열 진학이 많음 | 공학 계열 진학 사례가 많았음 |

질문 2: 앞에서 적은 학교 환경의 각 특징에 대해, 본인은 어떻게 대응했는지 알려주세요.

| 내부 행 ID | 원본 행 ID | 참조하는 특징 | 본인의 대응 |
| --- | --- | --- | --- |
| response-a | trait-a | 수시 진학 비중이 높음 | 활동 사이의 연결을 중심으로 상담했다. |
| response-b | trait-b | 특정 계열 진학이 많음 | 관심 전공과 탐구 주제의 연결을 살폈다. |

위 ID는 설명용 별칭이며 실제로는 안정적인 UUID를 사용한다. 배열 순번·질문 번호·열 라벨·답변 문자열로 연결하지 않는다. 같은 문장을 적은 두 행도 서로 다른 행일 수 있다.

### 작성 중

- 같은 응답 세션 안의 원본 질문·답변·행 ID로 연결한다. 다른 컨설턴트나 다른 응답 세션을 기본 참조 범위에 포함하지 않는다.
- 원본 행의 특징 등 지정한 기준값이 입력되면 후속 행을 만든다. 완전히 빈 임시 행은 제외한다. 원본 행의 나머지 필수값 검증도 유지한다.
- 행 추가 시 후속 행을 추가하고, 재시도로 같은 원본 행의 후속 행을 중복 생성하지 않는다.
- 원본 행 재정렬 시 후속 행도 순서를 따르지만 작성한 대응은 원본 행 ID와 계속 연결된다.
- 실제 참조하는 문구·설명이 바뀌면 표시를 갱신하고 기존 대응은 보존하되 `needs_review`로 표시한다. 최신 맥락을 확인해야 다시 확정할 수 있다.
- 원본 행 삭제 또는 비활성화 시 후속 행도 현재 유효 답변에서 제외한다. 작성 중 입력은 복구 가능한 비활성 상태로 보존한다. 작성된 후속 답변이 있는 삭제는 영향을 알리고 확인한다.
- 같은 ID의 행을 복구하면 입력도 복원할 수 있다. 문장이 같아도 새 ID의 행에 과거 대응을 자동으로 붙이지 않는다.
- 참조 셀은 후속 질문에서 직접 수정하지 않는다. 서버가 원본 값을 읽으며 클라이언트가 보내는 참조 문구를 신뢰하지 않는다.
- 재확인 여부에는 실제로 쓰는 값·설명의 해시를 사용한다. 무관한 형제 행의 수정으로 모든 답변을 재확인시키지 않는다.

연쇄 참조의 원본이나 중간 답변이 확인 대기라면 그 맥락을 쓰는 후속 답변도 확정하지 않는다. 순환 참조는 금지한다.

참조할 유효 행이 0개이면 후속 행도 0개이며 '참조할 항목 없음'으로 건너뛴다. 반드시 후속 답변을 수집하려면 원본 질문에 최소 1개의 유효 행을 요구한다. 원본 행 수와 무관하게 후속에 최소 1행을 요구하여 입력할 수 없는 상태를 만들지 않는다.

### 확정 이후

독립 자료에는 **참조 ID와 당시의 텍스트 스냅샷을 모두 보존**한다.

- ID: 원본 수정본 ID, 원본 행 ID, 사용한 열 ID. 원본 자료 ID는 수정본을 통해 알 수 있다.
- 스냅샷: 당시 질문과 실제 사용한 특징·설명·열 라벨·선택 라벨 등. 대상 수정본의 맥락 또는 참조 셀 스냅샷으로 보존한다.
- 관계: 대상 수정본·행과 원본 수정본·행·열을 연결하여 출처 및 변경 영향을 조회한다.

원본의 최신 문구를 실시간으로 붙여 과거 대응을 재해석하지 않는다. 원본이 수정되면 관련 자료에 변경을 알리고, 검토 후 새로운 대상 수정본을 만든다. 이전 대상 수정본은 이전 원본을 계속 가리킨다.

실제로 사용하는 필드와 맥락이 달라졌을 때만 재확인을 요구한다. 확인 대기는 자료의 현재 사용 상태로 관리하며 이미 확정한 수정본의 원문을 변경하는 상태가 아니다.

현재 기준 지식을 제공하는 기본 검색에서는 참조 맥락이 바뀌어 확인 대기인 대상을 보류한다. 과거 시점 조회에서는 원본 시점과 함께 사용할 수 있다. 원본 보관 시에도 현재 사용 여부를 재검토하되 과거 기록을 지우지는 않는다. 실제 내용 삭제가 필요한 경우에는 복사된 스냅샷과 AI 자료까지 참조 관계로 추적해야 한다.

### 텍스트와 RAG

질문 2의 한 행은 다음처럼 독립적으로 이해할 수 있어야 한다.

```text
질문: 앞에서 적은 학교 환경의 각 특징에 대해, 본인은 어떻게 대응했는지 알려주세요.
학교 환경의 특징: 수시 진학 비중이 높음
구체적인 설명: 학생부종합전형 진학 사례가 많았음
본인의 대응: 활동 사이의 연결을 중심으로 상담했다.
```

질문 전체의 텍스트는 유효 행을 라벨과 구분으로 이어 만든다. 긴 표를 행별 검색 조각으로 나누면 질문과 해당 행의 참조 맥락을 각 조각에 포함하고 수정본 ID·행 ID를 연결한다. 각 조각에 전체 원본 표를 반복하지 않는다. 사용자가 보지 못한 내부 설명·검토 요청이나 AI의 재작성을 컨설턴트의 원문에 섞지 않는다.

## 조건부 질문의 공통 규칙

조건부는 별도의 입력 유형이 아니다. 모든 입력 유형에 붙는 공통 규칙이다. 표시용 텍스트가 아니라 타입 있는 열 값과 유효한 행을 평가한다.

| 규칙 | 의미 | 예시 |
| --- | --- | --- |
| `applicable_when` | 이번 응답에 해당하는 질문인가 | 근무 경험에서 고등학교를 선택함 |
| `enabled_when` | 지금 작성할 수 있는가 | 앞선 질문의 유효한 답변이 완성됨 |
| `required_when` | 참여 중인 질문에 답변이 필수인가 | 특정 선택을 한 경우 이유가 필수 |

적용 대상이 아닌 질문은 숨기거나 안내로 표시한다. 작성 가능 조건을 기다리는 질문은 대기 상태로 표시한다. 일반적인 제출 완료 읽기 전용 잠금, 참조 셀의 읽기 전용 표시와는 구분한다. 접기/펼치기·페이지 이동도 적용 여부를 바꾸지 않는다. 필수 검사는 적용되고 작성 가능한 질문에 대해서만 수행한다.

처음에는 질문 단위 조건과 참조할 행의 필터부터 제공한다. 같은 규칙 형식을 이후 열의 필수 조건이나 행별 조건으로 확장할 수 있다. 제작자는 질문·열·연산자·비교값과 '모두 만족/하나 이상 만족' 그룹을 선택한다.

### 조건 저장

임의 JavaScript나 SQL 문자열을 실행하지 않고 허용된 연산자의 JSON 조건 트리를 저장한다. 아래 ID는 설명용 별칭이다.

```json
{
  "all": [
    {
      "op": "includes",
      "ref": { "question_id": "q_work", "field_id": "f_school_types", "scope": "singleton" },
      "value": "option_high_school"
    },
    {
      "op": "gte",
      "ref": { "question_id": "q_importance", "field_id": "f_score", "scope": "singleton" },
      "value": 4
    }
  ]
}
```

의미는 '근무 경험에 고등학교를 선택했고, 중요도가 4 이상'이다. 선택지는 라벨 대신 ID를 비교한다.

초기 연산은 `all`/`any`/`not`, 유효 답변의 유무·완성 여부, 명시적인 빈 값 판정, 타입별 등치·포함·숫자 비교, 행 수와 행 단위 조건으로 제한한다. 문자열/숫자의 암묵적 변환이나 임의 함수를 허용하지 않는다. 조건의 깊이·노드 수·참조 수에 상한을 둔다.

반복 행은 '이 행', '지정한 행', '하나 이상의 행', '모든 행', '조건을 만족하는 행 수'를 명시한다. '같은 행에서 특징 A이고 중요도 4 이상'은 `any_row` 안의 `all`로 묶는다. 서로 다른 행이 각각 조건을 만족하는 것을 같은 행으로 오인하지 않는다. 대상 행이 0개일 때 '모든 행'은 거짓으로 정한다. 빈 집합을 조건으로 삼으려면 명시적으로 행 수 0을 사용한다.

### 미응답과 조건 변경

- 값 비교는 참·거짓·미확정의 세 상태로 평가한다. 미응답을 'A가 아님'으로 취급하지 않으며 `not(미확정)`도 미확정이다.
- `all`은 거짓이 하나라도 있으면 거짓, 모두 참이면 참, 나머지는 미확정이다. `any`는 참이 하나라도 있으면 참, 모두 거짓이면 거짓, 나머지는 미확정이다.
- 유효한 숫자 0이나 불리언 false는 빈 값이 아니다. 빈 값·응답 있음 연산은 별도 정의를 갖는다. 서식만 있는 빈 답변은 일반 텍스트를 기준으로 판정한다.
- 비활성 질문에 남아 있는 예전 값을 다른 조건의 근거로 사용하지 않는다.
- 비해당이 된 입력은 작업 중 자료로 보존하지만 필수 검사·완료율·독립 자료 생성·AI 이용에서 제외한다. 빈 독립 자료를 대신 생성하지 않는다.
- 조건이 다시 성립하면 입력을 복원할 수 있다. 실제 참조 내용이나 분기의 의미를 결정하는 값이 바뀌었다면 재확인한다.
- 선택 입력인 전제 질문이 미응답이면 제출 시 후속을 '전제 미응답으로 건너뜀'으로 기록할 수 있다. 필수 전제가 미응답이면 제출을 막는다. 반드시 받아야 하는 후속 답변의 전제는 제작자가 필수로 설정해야 한다.
- 전제의 '완성'은 현재 입력의 유효성 검사를 통과한 상태다. 같은 질문지 전체의 제출 완료를 기다리는 조건은 허용하지 않는다.

### 의존 관계와 검증

조건 참조, 같은 행의 열 참조, 참조형의 행 생성 관계를 하나의 의존 그래프로 검사한다. 질문·열·행 범위에 맞춰 순환·자기 의존·존재하지 않는 참조·타입 불일치를 검출한다. 반복 평가가 언젠가 수렴할 것이라고 가정하지 않는다.

제작 UI는 앞선 질문을 참조하는 것을 기본으로 한다. 게시·배포 검증은 표시 순서와 무관하게 그래프에 순환이 없는지 검사한다. 같은 행의 다른 열 조건도 대상 열의 유효성에 다시 의존하는지 확인한다. 참조 중인 질문·열·선택지를 삭제하려면 관련 설정을 먼저 해소해야 한다.

질문 정의·규칙·라벨·행 참조는 배포 버전에 고정한다. 진행 중인 응답에 다른 버전의 규칙을 적용하지 않는다. 편집 가능한 초안의 정의가 바뀌면 기존 입력과의 호환성을 검사한다.

브라우저에서 즉시 평가하고 서버에서 같은 의미로 다시 평가한다. 클라이언트가 보낸 표시·유효·완성 상태를 제출 근거로 신뢰하지 않는다. 직접 DB 쓰기를 열지 않고 타입·참조·권한·revision을 검증하는 저장 경로로 제한한다.

## 저장과 제출

질문지 안에서는 전제 변경이 여러 후속 질문에 영향을 주므로 응답 전체 revision을 유지한다. 부분 변경 API를 추가해도 최신 응답에 변경을 적용한 다음 영향받는 조건과 참조를 평가한다. 독립 자료 편집에서는 자료별 revision을 사용한다.

제출할 때는 다음을 같은 확정 대상 입력으로 원자적으로 처리한다.

1. 본인 권한, 응답, 배포 정의와 기대 revision을 확인한다.
2. 의존 순서에 따라 참여 질문·행, 건너뜀 사유, 참조 확인 상태를 판정한다.
3. 참여 대상의 필수값·타입·범위·행 수를 검증하고 참조 값을 서버에서 해결한다.
4. 유효 답변이 있는 질문마다 독립 자료와 초기 수정본을 생성하고, 원본과 후속의 수정본 ID를 대응시킨다.
5. 참조 스냅샷·관계·일반 텍스트를 저장한다.
6. 제출 원본과 생성한 수정본 링크, 참여/제외 판정을 고정한다.

검증 이후 전제가 바뀌면 revision 충돌로 처리한다. 원본과 후속을 서로 다른 시점의 값으로 확정하지 않는다. 재시도로 행·자료를 중복 생성하지 않으며, 자료 생성 실패 시 제출만 완료되는 부분 성공을 허용하지 않는다. 임베딩 API는 이 처리 밖에서 호출하고, 커밋된 수정본의 작업을 재시도할 수 있게 한다.

독립 편집도 구조·텍스트·참조를 하나의 새 수정본으로 확정한다. 과거 제출 원본과 후속 자료를 자동으로 바꾸지 않는다. 원본 갱신 시 최신 사용 상태와 영향받는 자료를 확인한다.

## API와 활용

다음은 새 계약의 예시이며 현재 구현이 아니다.

| API | 책임 |
| --- | --- |
| 기존 질문지 API | 질문 정의, 작성 중 구조 데이터, 응답 revision, 제출 |
| `GET /api/consultant-qa` | 본인 자료를 질문 단위로 목록·검색 |
| `POST /api/consultant-qa` | 질문지 없이 등록. 텍스트 입력도 공통 1행1열로 변환 |
| `GET/PATCH /api/consultant-qa/:id` | 구조·텍스트 조회, 기대 revision을 포함한 구조 편집 |
| `GET /api/consultant-qa/:id/revisions` | 과거 수정본과 당시 참조 조회 |
| `GET /api/consultant-qa/:id/references` | 권한 범위 안에서 참조와 변경 영향 조회 |

독립 자료끼리 연결할 때도 원본 수정본 ID를 선택하여 고정한다. 기존 자료의 재수집은 업데이트 대상을 명시해야 하며 질문 문장의 일치만으로 이전 자료를 덮어쓰지 않는다.

AI용 데이터는 현재 확정됨·유효함·이용 대상임을 충족하는 수정본만 사용한다. 작성 중, 비해당, 빈 답변, 원본 변경 확인 대기는 현재 검색에서 제외한다. 컨설턴트 ID와 이용 권한은 서버에서 검증하며, 본인의 원문과 AI 요약·추측을 구분한다.

RAG에는 질문·필요한 분기 맥락·참조 맥락·해당 답변을 포함한다. 조건식 전체나 모든 선행 답변을 무조건 포함하지 않는다. 파생 자료에 수정본 ID·행 ID·추출 규칙 버전·입력 해시를 연결하고, 오래된 작업 결과가 최신 검색 자료를 덮어쓰지 않도록 한다.

학습 데이터는 사용한 수정본의 집합과 정형화 규칙을 고정한다. 실제 상담 입력과 원하는 출력으로 별도 선별·평가하며, 원본 수정이 과거 학습된 모델을 자동으로 수정하지는 않는다.

## 도입 순서와 확인할 동작

기존 4가지 유형을 공통 정의와 1행 답변으로 변환하는 계약, 독립 자료와 수정본, 텍스트 생성을 먼저 만든다. 이후 반복 표와 안정적인 행 ID, 참조형, 공통 조건 평가를 구현한다. ID·참조·조건 의존성의 계약은 처음부터 함께 설계한다.

기존 `selection`과 새 `answer_data`를 각각 수정하는 구조는 피한다. 이전 입력을 변환하고 호환 조회하는 경계를 두되 새 쓰기의 기준은 하나로 정한다. 질문·선택지·답변 ID를 가능한 한 유지하고, 자유 응답도 질문 없는 메모라는 출처를 보존한다.

구현 시 확인할 대표 사례:

- 기존 선택·직접 입력·추가 서술·RichText가 손실 없이 변환된다.
- 행 추가·재정렬·같은 문구의 중복 행·삭제/복원 뒤에도 대응을 바꾸어 붙이지 않는다.
- 원본 변경 시 후속 입력이 사라지거나 재확인 없이 최신 지식에 들어가지 않는다.
- 미응답의 부정, 0/false, 다수선택, 빈 행 집합, 같은 행 안의 복합 조건이 정해진 의미로 평가된다.
- 비활성 입력을 조건·필수 검사·진행률·AI 출력에 사용하지 않는다.
- 순환, 잘못된 타입, 다른 사용자·버전·세션·존재하지 않는 행에 대한 참조를 거절한다.
- 동시 편집·재전송·제출 실패에서도 중복이나 부분 확정을 남기지 않는다.
- 독립 자료 수정 후에도 제출 당시 원본과 과거 수정본을 재현한다.
- 브라우저와 서버의 조건 평가가 일치하고 서버가 조작된 유효 상태를 거절한다.

로컬 답변 0건은 운영 데이터도 없다는 의미가 아니다. 실제 구현·이관 시 대상 데이터와 이력을 다시 확인한다. [로컬 Supabase 운영 주의](local-supabase.md)에 따라 이력 동등성 검토 없이 운영 `db push`, reset, migration repair를 실행하지 않는다.
